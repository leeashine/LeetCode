# 回顾：这份笔记为什么需要这些记录和方法

[← 有条件地回收](09-墓碑GC.md) ｜ [目录](../README.md)

**本课任务**：不用背类名，从一篇笔记的同步问题解释每个数据部件。完成后，能说明新增方法是被哪个需求带出来的。

**阅读约定**：本章沿用前面各章的记号。手机简记为 **A**，电脑简记为 **B**。**A2/B1** 表示一张记录：它知道 A 的 2 次操作、B 的 1 次操作。第 4 章用它记标题的修改次数，第 9 章用它记已应用的操作进度。**A1** 单独出现时表示 A 发出的第 1 张添加票（第 5 章）。

## 1. 每章让应用多会了什么

| 任务 | 裸值无法回答的问题 | 保存的记录 | 引出的核心方法 |
|---|---|---|---|
| 统计操作 | 两个 3 是独立贡献还是重复历史 | 每个来源的累计次数 | increment、merge、value |
| 统计净增减 | 直接减小会被旧的大值覆盖 | 累计新增 P、累计删除 N | increment、decrement、分别 merge |
| 标题只留一个 | 晚到的消息不一定更新 | 顺序标记及来源 | 时钟 observe/tick、set、merge |
| 标题保留独立修改 | 保存时是否知道对方的修改 | 每份候选内容的修改记录 | version、assign、dominates、merge |
| 标签增删 | 取消的是旧添加还是所有未来添加 | 添加票与墓碑 | add、remove、merge（先汇总再剪枝） |
| 正文编辑 | 同一下标是否还是同一字符 | 字符 ID、锚点、墓碑 | insert、delete、merge、text（遍历） |
| 少发数据 | 只发变化时，重发怎样不算重 | 可合并的小片段与待发记录 | pending、apply、ack |
| 部分回收 | 删除是否共同收到，旧记录是否还会来 | 进度、删除见证、结构依赖 | frontier、covers、gc |

同一个方法名在不同类型上职责不同。版本向量的 merge 汇总经历，MVRegister 的 merge 筛选候选内容。读一个方法时，先看它接什么、返回什么，不要只记名字。

## 2. 遇到新需求，怎样想出一个方法

**假设**

应用提出新需求：界面要标出“标题还有独立修改待选择”。事情按这个顺序发生：

```text
① 手机保存标题“六点”。手机不知道电脑的修改。记录是 A1/B0
② 电脑保存标题“七点”。电脑不知道手机的修改。记录是 A0/B1
③ 两台设备同步。两边都有两份候选：六点 A1/B0、七点 A0/B1
④ 界面要决定：是否显示“待选择”标记
```

**问题**

直接先写一串 API，还是先把输入和结果写清楚？

**解释**

先把输入和结果写清楚。选上面这段例子，沿这条顺序走：

```text
要完成什么动作
→ 手里有什么状态
→ 期望拿到什么结果
→ 缺哪种记录或判断
→ 把这件事命名为一个方法
→ 实现并验证这段例子
```

用第 ④ 步的需求逐项走一遍：

| 链条步骤 | 本例的答案 |
| --- | --- |
| 要完成什么动作 | 标出“标题有待选择的独立修改” |
| 手里有什么状态 | 两份候选内容，各带一张修改记录 |
| 期望拿到什么结果 | 一个判断：有待选择 / 没有待选择 |
| 缺哪种记录或判断 | 候选数量。记录已够用，不缺新记录 |
| 把这件事命名为一个方法 | `size()`：候选数大于 1 时标出 |
| 实现并验证这段例子 | 合并 ③ 的状态，`size()` 得 2，标出 |

换一个需求再走一遍：准备淘汰旧标题。

| 链条步骤 | 本例的答案 |
| --- | --- |
| 要完成什么动作 | 丢掉已被替换的旧标题 |
| 手里有什么状态 | 新记录 A2/B1，旧记录 A1/B0 |
| 期望拿到什么结果 | 一个判断：旧标题是否已过时 |
| 缺哪种记录或判断 | 缺“新记录是否知道旧经历”的逐栏比较 |
| 把这件事命名为一个方法 | 先建 `greaterOrEqual`，再组合出 `dominates` |
| 实现并验证这段例子 | A 栏 2≥1，B 栏 1≥0，且 A 栏更多，淘汰旧标题 |

`values()`、`isEmpty()` 也来自这条链。页面要列出可见内容，要判断空状态。它们是读取便利，不是另一种更新算法。

字段同理。每个字段必须说得出它防住哪个反例。空起点、内部构造器、只读快照、相等与哈希也不是装饰。它们让上面的规则在 Java 对象中保持一致。

## 3. 用三段故事检查理解

**故事一：A2/B1 与 A1/B3 合并，再送一次 A1/B3**

**假设**

两台设备统计各自的操作次数。事情按这个顺序发生：

```text
① A 做 1 次操作，A 的记录是 A1。A 同步给 B，B 收到 A1
② B 做 1 次操作，B 的记录是 A1/B1。B 同步给 A，A 收到后也是 A1/B1
③ A 又做 1 次操作，A 的记录是 A2/B1
④ B 又做 2 次操作，B 的记录是 A1/B3
⑤ A 与 B 互相同步
⑥ 网络把 B 在 ④ 的记录 A1/B3 又发给 A 一次
```

**问题**

⑤ 之后总操作数是多少？⑥ 的旧记录为什么不让总数继续增加？

**解释**

先演算 ⑤ 的合并：

```text
merge(A2/B1, A1/B3)
  A 栏：max(2, 1) = 2
  B 栏：max(1, 3) = 3
  结果：A2/B3，总数 = 2 + 3 = 5
```

再演算 ⑥ 的重发：

```text
merge(A2/B3, A1/B3)
  A 栏：max(2, 1) = 2，不变
  B 栏：max(3, 3) = 3，不变
  结果：仍是 A2/B3，总数仍是 5
```

逐步说明：

1. merge 逐来源保留较大累计值。它不把两栏相加。
2. A 栏的 2 已包含 A 的第 1 次操作。B 栏的 3 已包含 B 的前 2 次操作。
3. 重发的 A1/B3 与已知历史重叠。它的每一栏都不超过已有记录。
4. 取 max 后状态不变。总数仍是 5。
5. value 求和只在读取总数时做一次。合并阶段不求和。

**故事二：A、B 各写六点、七点，手机收到两份后又保存一次七点**

**假设**

事情按这个顺序发生：

```text
① 手机保存标题“六点”。手机不知道电脑的任何修改。六点的记录是 A1/B0
② 电脑保存标题“七点”。电脑不知道手机的任何修改。七点的记录是 A0/B1
③ 两台设备联网，互相同步。两台设备都知道两份候选
④ 用户在手机上看到两份标题，选择“七点”，在手机上再保存一次。这是手机的第 2 次保存
```

**问题**

为什么 ③ 之后有两个值，④ 之后只剩一个？

**解释**

先演算 ③ 的合并：

```text
六点 A1/B0 与 七点 A0/B1 逐栏比较
  A 栏：六点有对方不知道的 A1
  B 栏：七点有对方不知道的 B1
  互不包含，两份候选都保留
  values = [六点, 七点]，size = 2
```

再演算 ④ 的保存。assign 分两步：

```text
version() = merge(A1/B0, A0/B1) = A1/B1   ← 先汇总两份经历
increment(A)：A 栏 1 → 2                  ← 再推进本设备
新七点的记录 = A2/B1
```

检查新记录能否替换两份旧候选：

```text
A2/B1 对 六点 A1/B0：A 栏 2≥1，B 栏 1≥0，且 A 栏更多 → dominates → 淘汰
A2/B1 对 七点 A0/B1：A 栏 2≥0，B 栏 1≥1，且 A 栏更多 → dominates → 淘汰
```

逐步说明：

1. ③ 的两次保存互相独立。两份都保留，由用户选择。
2. 接收两份不会自动选择。只有再次保存才表达决定。
3. ④ 的新记录 A2/B1 先继承两份经历，再多出一次保存。
4. 所以 A2/B1 能替换两者。结果 values = [七点]，size = 1。

**故事三：A 删除标签票 A1，B 并发新加 B1；共同收到删除并回收后，旧的仅添加快照又回来**

**假设**

标签是“工作”。规定成员只有 A、B。删除见证记为（设备， 第几次有效操作）。事情按这个顺序发生：

```text
① 手机添加“工作”，发出票 A1。这是 A 的第 1 次有效操作
② 手机同步给电脑。电脑收到 A1
③ 手机取消“工作”。手机只见过 A1，只为 A1 记录墓碑。删除见证是 (A,2)，进度推进到 A2
④ 电脑在收到取消之前又添加一次“工作”，发出票 B1。这是 B 的第 1 次有效操作
⑤ 两台设备互相同步。电脑收到取消，手机收到 B1
⑥ 双方计算共同进度，回收 A1 的墓碑
⑦ 一份旧快照到达。它是 ② 之前保存的手机状态：只有添加 A1，没有删除证据
```

**问题**

⑤ 之后“工作”为什么留下？⑦ 之后为什么仍可能不安全？

**解释**

先演算 ⑤ 的合并。规则是先汇总，再剪枝：

| 阶段 | “工作”的票 | 墓碑 |
| --- | --- | --- |
| 汇总 | A1、B1 | A1 |
| 剪枝 | B1 | A1 |

1. 手机在 ③ 取消时不知道 B1。删除只针对已收到的 A1。
2. 汇总后“工作”的票是 A1、B1。墓碑是 A1。
3. 剪枝移除墓碑票 A1。B1 留下。
4. “工作”继续存在。这是第 5 章的规则：删除只处理已收到的添加。

再演算 ⑥ 的回收：

```text
⑤ 之后双方的进度表都是 A2/B1
frontier = 逐栏取 min(A2/B1, A2/B1) = A2/B1
covers(frontier, (A,2))：frontier 的 A 栏 2 ≥ 2 → true
gc：移除 A1 的墓碑和删除见证
回收后的状态：票 = {B1}，墓碑 = {}，进度表仍是 A2/B1
```

最后演算 ⑦ 的旧快照合并：

```text
旧快照：票 = {A1}，墓碑 = {}
当前状态：票 = {B1}，墓碑 = {}
汇总：票 = {A1, B1}，墓碑 = {}
剪枝：没有墓碑票可移除
结果：A1 重新进入“工作”的票集
```

逐步说明：

1. 回收后，A1 的删除证据已经不存在。
2. 当前 merge 不检查“这张票是否早于回收前沿”。
3. 所以旧快照里的 A1 复活。
4. 本例中 B1 仍在，“工作”的显示没有变化。第 9 章第 8 节的例子没有 B1，同一过程让已删除的标签重新显示。
5. 合并规则本身没有错。旧快照确实不在当前墓碑里。
6. 结论：正确的合并规则不等于完整的回收协议。还需要额外约束：成员固定，删除前的快照不再进入同步，或引入消息屏障、有效基线。

## 4. 三个层次各自负责什么

- 业务选择：标题留一个还是多个，标签的并发添加是否存活。
- 数据类型：保存记录，定义本地更新，定义合并和查询。
- 同步与生命周期：送达，重试，按批次确认，持久化，成员管理，旧快照处理，身份分配。

每一层都不能替另一层保证：

1. 合并算法不会送达永远丢失的消息。
2. 测试两边相等不会保证业务内容正确。
3. 稳定前沿不会让旧备份自动消失。
4. equals 排除某个字段，不表示持久化可以不保存它。

## 5. 先补最有意义的下一步

把本课自己的小故事加入 [ConvergenceLearningTest](../../../../test/java/crdt/learnning/ConvergenceLearningTest.java)。覆盖一条轨迹：修改 → 同步 → 继续修改 → 旧快照晚到。再根据实际目标选择进阶方向：按批次确认、持久高水位，或有版本的压实基线。

有些需求超出本课程的范围：全局额度、线性一致读写、跨对象事务。它们需要另外的协调机制。注意两条边界：

1. 计数能收敛，不自动保证库存非负。
2. 共识能达成一致，不自动补齐事务。

术语速查：

| 术语 | 含义 |
| --- | --- |
| merge / join | 按规定汇总两份信息 |
| 幂等、交换、结合 | 重复、换序、分组不改变结果 |
| 版本向量 | 按来源记录修改进度的表 |
| 票（Tag） | 标识一次添加 |
| 墓碑 | 保存删除证据 |
| 稳定前沿 | 规定成员都完整应用历史的共同进度 |
