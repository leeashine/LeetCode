## 1. 每章让应用多会了什么

| 任务 | 裸值无法回答的问题 | 保存的证据 | 引出的核心方法 |
|---|---|---|---|
| 统计操作 | 两个 3 是独立贡献还是重复历史 | 每来源累计量 | increment、merge、value |
| 统计净增减 | 直接减小会被旧大值覆盖 | 增加量 P、减少量 N | decrement、分别 merge |
| 标题只留一个 | 消息后到不代表更新 | 修改标签及来源 | 时钟 observe/tick、set、merge |
| 标题保留独立修改 | 新写是否收到过旧写 | 每候选内容的次数表 | version、assign、比较、merge |
| 标签增删 | 取消的是旧添加还是所有未来添加 | 添加票及删除票 | add、remove、剪枝 merge |
| 正文编辑 | 同一下标是否还是同一字符 | 字符 ID、锚点、墓碑 | insert、delete、遍历 text |
| 少发数据 | 重发小变化怎样不算重、不漏发 | 小状态片段与待发记录 | pending、apply、ack |
| 部分回收 | 删除是否共同收到，旧记录是否还会来 | 进度、删除见证、结构依赖 | frontier、covers、gc |

同一个名称也有不同职责：版本向量 merge 汇总经历，MVRegister.merge 筛选候选内容。先看它接什么、返回什么，别只记名字。

## 2. 遇到新需求，怎样想出一个方法

**假设**：下一步需要在界面标出“哪些字段还有独立修改待选择”。

**问题**：直接先写一串 API，还是先把输入和结果写清楚？

**解释**：先选一段例子，再沿这条顺序：

```text
要完成什么动作
→ 手里有什么状态
→ 期望拿到什么结果
→ 缺哪种记录或判断
→ 把这件事命名为一个方法
→ 实现并验证这段例子
```

例如准备淘汰旧值，要知道新记录是否包含旧经历，所以先建立逐栏比较，再组合“严格更多”的判断。为了统计当前可见值，再增加 values/size，它们是读取便利，而不是另一种更新算法。

字段同理：必须说得出它防住什么反例。实现空起点、内部构造器、只读快照、相等与哈希，是让这些规则能在 Java 对象中保持一致的需要。

## 3. 用三段故事检查理解

**故事一**：A2/B1 与 A1/B3 合并，再送一次 A1/B3。

**问题**：总操作数是多少，为什么不继续增加？

**解释**：A2/B3，总数 5；同来源的历史重叠，只保留较大累计值。

**故事二**：A、B 各写六点、七点，手机收到两份后又保存一次七点。

**问题**：为什么独立修改先有两个值，最后只有一个？

**解释**：最初 A1/B0 与 A0/B1 互不包含；新保存是 A2/B1，继承两份经历并多出修改，可以替换两者。接收不会自动替用户选择，保存才表达新的决定。

**故事三**：A 删除标签票 A1，B 并发新加 B1；之后共同收到删除并回收，旧的仅添加快照又回来。

**问题**：前半段为什么 B1 留下，后半段为什么仍可能不安全？

**解释**：A 未收到 B1，删除只针对 A1；GC 后当前算法忘掉 A1 的删除证据，又不拒绝旧快照，所以 A1 可能复活。合并规则正确不等于完整回收协议已具备。

## 4. 三个层次各自负责什么

- 业务选择：标题留一个还是多个、标签的独立添加是否存活。
- 数据类型：保存信息、定义本地更新、合并和查询。
- 同步与生命周期：送达、重试、确认批次、持久化、成员、旧快照与身份分配。

算法不会送达永远丢失的消息。测试相等不会保证内容正确。前沿不会让旧备份自动消失。相等排除某个字段，也不表示持久化可以不保存它。

需要全局额度、线性一致读写或跨对象事务，另外设计协调机制；计数能收敛，不自动保证库存非负，共识也不自动补齐事务。

术语速查：merge/join 是按规定汇总信息；幂等、交换、结合分别描述重复、换序、分组不变；版本向量是按来源记进度的表；tag 标识一次添加，墓碑保存删除证据；稳定前沿是规定成员完整应用历史的共同进度。
