# 总结与自检

## 1. 一页纸总结

| 你遇到的问题 | 用哪个 CRDT | 一句话记忆 |
|---|---|---|
| 多机计数 | `GCounter` / `PNCounter` | 各写自己那一格，读的时候求和 |
| 单值覆盖，最后写赢 | `LWWRegister` | 时间戳大者胜，撞车比 ID |
| 并发写不能丢 | `MVRegister` | 版本向量判并发，两个都留 |
| 集合增删 | `ORSet` | 每次 add 发唯一票，remove 只撕自己看见的票 |
| 文本编辑 | `RGA` | 字符挂父指针，同层按 ID 降序前序遍历 |
| 带宽太大 | delta-state | 只传增量，增量本身也是半格元素 |
| 内存无限涨 | 墓碑 GC + 因果稳定 | 所有副本都见过的墓碑才能丢 |
| 需要强一致 + 事务 | （不是 CRDT） | 该上 Raft/Paxos |

## 2. 收敛性自检清单（写任何新 CRDT 都过一遍）

- [ ] `merge` 幂等？（重复投递安全）
- [ ] `merge` 交换？——**每一对状态都要验，别只挑一对**
- [ ] `merge` 结合？（多跳转发安全）
- [ ] 有底元素？（空副本加入不污染别人）
- [ ] 每个分量都是**单调**的？（只增不减：max、并集、墓碑集合）
- [ ] `equals` 只比**被复制的状态**，不含本地身份/本地缓冲/因果元数据？
- [ ] 跑过 `LatticeLawsTest` + `ConvergenceTest` 的 25 个种子？
- [ ] 如果有墓碑/缓冲：有没有因果稳定的回收路径？回收后会不会复活数据？

## 3. 常见误区（小白最容易踩，前两条是本项目真实踩过的）

| 误区 | 后果 | 正解 |
|---|---|---|
| 用 `merge` 做求和/覆盖 | 幂等挂掉，重传就出错 | 只用 max / 并集这类单调运算 |
| 定律测试只验一对状态的交换律 | 放过真实 bug（本项目放过了一个） | 交换律对**每一对**都验 |
| 只测"先写完再同步"的时序 | 时序相关的 bug 被掩盖（本项目掩盖过一个） | 覆盖"写一半→同步→再写" |
| 把本地计数器放进 `equals` | 副本永远"不相等"，收敛测试假失败 | 本地状态与被复制状态严格分离 |
| `replicaId` 重复 | 标识符撞车，`merge` 抛异常 | 全局唯一且稳定 |
| 用物理时钟做时间戳 | 时钟回拨导致旧写覆盖新写 | 用 Lamport / 版本向量 |
| 以为"收敛"就是"正确" | 大家一致但顺序不符合用户预期 | 收敛性和意图保持分别设计、分别测试 |
| 按"时间窗"回收墓碑 | 数据复活 | 按**因果稳定**回收 |
| 以为 delta-state 不用改协议 | 信息只走一跳，永远不收敛 | 广播+全员确认，或交换因果上下文 |

## 4. 延伸方向

1. **全量压实（compaction）**：RGA 中段墓碑无法回收，需要"同一稳定前沿上重建文档基线"，这是第 9 步之后的下一个台阶
2. **属性测试**：把固定种子换成 jqwik / QuickTheories，随机生成操作**与时序**
3. **压缩**：RGA 每字符一节点开销大，Yjs 用 run-length 编码 + 富文本属性表
4. **网络与持久化**：序列化、gossip 调度、快照恢复——这些是纯工程，CRDT 只把"冲突解决"这一块变成了纯函数
5. **CRDT + 共识的取舍**：需要"强一致 + 事务"时，CRDT 不合适，该上 Raft

## 5. 术语表

| 术语 | 含义 |
|---|---|
| CRDT | Conflict-free Replicated Data Type，无冲突复制数据类型 |
| CvRDT | state-based CRDT，靠交换全量状态收敛 |
| δ-CRDT | delta-state CRDT，靠交换增量收敛 |
| replica / replicaId | 副本 / 副本的全局唯一标识 |
| merge / join | 半格上的"并"，CRDT 唯一的同步操作 |
| 半格（join-semilattice） | 有"并"运算且满足幂等/交换/结合的代数结构 |
| 底元素（bottom） | 半格最小元，merge 的单位元，对应"空副本" |
| Lamport 时钟 | 逻辑时钟，给出全序，但分不清并发 |
| 版本向量 | 因果历史计数器数组，给出偏序，能识别真并发 |
| tag | ORSet 中每次 add 的唯一票，用于 observed-remove |
| 墓碑（tombstone） | 删除标记，只增不减，需要因果稳定后 GC |
| 反熵（anti-entropy） | 副本之间周期性地互相 merge 以收敛 |
| 因果稳定（causal stability） | 某个事件已被所有副本观察到；墓碑可回收的前提 |
| 稳定前沿（stability frontier） | 所有副本 version 向量的逐分量最小值 |
| 复活（resurrection） | 已删除的数据因墓碑被过早回收而重新出现 |
| 压实（compaction） | 在稳定前沿上重建基线，彻底清除墓碑（RGA 中段墓碑的唯一出路） |

---

**最后一句**：CRDT 的难点从来不是分布式，而是**把业务语义翻译成一个单调的半格运算**。翻译对了，后面全是免费的；翻译错了，测试会告诉你——这就是本手册第 7 步存在的意义。

而比"写对 merge"更难的，是**写出能抓住错误的测试**：交换律要验每一对，时序要覆盖"写一半再同步"，语义要断言具体结果而不只是"大家一样"。本手册里两个真实踩坑（第 3 步、第 8 步）都出在测试而不是实现上。
