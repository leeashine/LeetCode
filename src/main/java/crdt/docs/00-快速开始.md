## 2. 三个核心名词，一次讲透

别背定义，先建立一个心智模型：**想象 5 台机器各拿着一份数据副本，网络会丢包、会重复、会乱序，而且任何时刻都可能断网。**

### 2.1 副本（replica）

一台机器上的一份数据。每份副本有一个**全局唯一**的名字，叫 `replicaId`。

> ⚠️ `replicaId` 必须唯一且稳定。两个逻辑副本用同一个 id，会生成相同的标识符，`merge` 时直接抛异常。这是 CRDT 唯一的硬性部署约束。

### 2.2 合并（merge）

副本之间同步时**唯一**的操作。它不是"覆盖"、不是"以谁为准"，而是**求并集/取更大值**这种"只会往前不会往后"的运算。

```
副本A.merge(副本B)  →  得到一个新状态，它同时包含 A 和 B 的全部信息
```

### 2.3 半格三律（CRDT 的全部秘密）

只要 `merge` 满足下面三条，那么**无论消息怎么丢、怎么重、怎么乱序，只要最后所有副本互相同步过一次，它们必然一模一样**：

| 定律 | 公式 | 换来的能力 |
|---|---|---|
| **幂等** | `a.merge(a) == a` | 重复投递安全 → 不需要去重，不需要 ACK 重传逻辑 |
| **交换** | `a.merge(b) == b.merge(a)` | 乱序到达安全 → 不需要排序缓冲 |
| **结合** | `(a.merge(b)).merge(c) == a.merge(b.merge(c))` | 多跳/中转同步安全 → 不需要中心节点 |

**这就是 CRDT 为什么是 AP 系统（可用 + 分区容忍）的基石**：断网时各写各的，恢复后 merge 一下自动一致，全程不需要任何"协商"。

> 换个说法：CAP 里的 C 通常要靠共识（Raft/Paxos）才能拿到；CRDT 走的是另一条路——**让"不一致"本身变成不可能，而不是去修复它**。

## 3. 环境与验证命令（重要）

本仓库的 `mvn compile` 已经损坏（`java8/chap6` 编码错误、`com.sun.*` 内部包等历史遗留，与 CRDT 无关），**所以不要用 mvn 验证本模块**。

用下面的命令，直接 `javac` + JUnit：

```bash
cd /Users/lizixuan/Documents/IdeaProjects/LeetCode

JAR="$HOME/.m2/repository/junit/junit/4.13.1/junit-4.13.1.jar:$HOME/.m2/repository/org/hamcrest/hamcrest-core/1.3/hamcrest-core-1.3.jar"

# 编译整个 crdt 模块（主代码 + 测试）
rm -rf /tmp/crdt && mkdir -p /tmp/crdt
javac -encoding UTF-8 -d /tmp/crdt -cp "$JAR" src/main/java/crdt/*.java src/test/java/crdt/*.java

# 跑全部测试
java -cp "/tmp/crdt:$JAR" org.junit.runner.JUnitCore \
  crdt.GCounterTest crdt.PNCounterTest crdt.LWWRegisterTest crdt.MVRegisterTest \
  crdt.ORSetTest crdt.RGATest crdt.LatticeLawsTest crdt.ConvergenceTest \
  crdt.DeltaGCounterTest crdt.DeltaORSetTest crdt.DeltaSyncTest crdt.TombstoneGcTest

# 跑可视化 demo（打印每一步的合并结果）
java -cp /tmp/crdt crdt.CrdtDemo
```
