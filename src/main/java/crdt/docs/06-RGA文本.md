## 1. 下标为什么不能直接拿来同步？

**假设**

事情按这个顺序发生：

```text
① A、B 的正文都是 ab
② A 在下标 1 插入 X；A 看到 aXb，B 不知道这次插入
③ B 在下标 0 插入 Y；B 看到 Yab，A 也不知道这次插入
④ B 收到 A 发来的操作“在下标 1 插入 X”，并照原样执行
```

两台设备各自的正文变化：

```text
A：ab → aXb
B：ab → Yab
```

**问题**

④ 之后，B 的正文是什么？错在哪里？

**解释**

1. B 的正文变成 `YXab`。
2. X 排在 a 前面。
3. A 的本意是 X 排在 a 后面。
4. ② 发生时，A 的下标 1 指向 a 与 b 之间。③ 之后，B 的下标 1 指向 Y 与 a 之间。
5. 同一个下标数字，在 B 插入 Y 后指向了另一个位置。

结论：下标只在产生它的那份正文里有意义。界面仍可使用下标输入，但状态要记“在原来那个 a 后面插入 X”。给每个字符一个稳定身份。即使正文里有两个 a，它们也能区分。

本章处理 Java 的 `char`：一个 UTF-16 代码单元。一个 emoji 可能占两个代码单元。本实现没有按用户看到的完整字符分段，也不支持富文本、光标、选区或撤销。

## 2. 先定义字符身份与锚点

**假设**

事情按这个顺序发生：

```text
① 设备 S 写出初始正文 ab，产生 a、b 两个节点
② S 把状态同步给 A 和 B
③ A、B 都收到这两个节点，正文都是 ab
```

两个节点的内容：

```text
a.id = (1, S)，a.parentId = null
b.id = (2, S)，b.parentId = a.id
```

`id` 是字符身份，`parentId` 是锚点。锚点记录“这个字符在谁后面”。`parentId = null` 表示挂在虚拟根下。虚拟根不是可见字符。

**问题**

A、B 各自产生下一个节点，编号都是 3。怎样避免身份相同？又怎样保留“插在 a 后”这个位置？

**解释**

1. 身份由两项组成：逻辑编号和设备 ID。
2. A 的新节点身份是 (3,A)，B 的新节点身份是 (3,B)。编号相同，设备 ID 不同，身份就不同。
3. 每个节点再记录两项：锚点和字符。
4. X、Y 的锚点都是 a 的身份 (1,S)。“插在 a 后”这个位置就这样保留下来。

先补 `NodeId(long timestamp, String replicaId)`：输入编号、设备 ID，返回不可变身份。`timestamp` 是逻辑编号，不是墙上时钟。比较规则：先比编号；编号相同，再按设备 ID 的字符串顺序比较：

```java
int byTimestamp = Long.compare(timestamp, other.timestamp);
return byTimestamp != 0 ? byTimestamp : replicaId.compareTo(other.replicaId);
```

用具体值检查这条规则：

```text
(2,S) 与 (3,A)：2 < 3，所以 (2,S) 排在前
(3,A) 与 (3,B)：编号相同，"A" 排在 "B" 前，所以 (3,A) 排在前
```

`equals` 比较这两项，`hashCode` 使用这两项。否则相同身份无法在 `Map` 中去重。

再补 `Node(NodeId id, NodeId parentId, char value)`：输入本节点身份、锚点、字符，返回不可变节点。节点相等必须比较三项。相同身份但不同锚点或字符意味着冲突，不能当成重复消息。

接着在骨架里定义状态字段：

```java
String replicaId;             // 本设备后续写入使用的身份
Map<NodeId, Node> nodes;       // 所有字符节点，包括已删除的
Set<NodeId> tombstones;        // 本章只保存已删除字符 ID
```

三个字段各管一件事。`replicaId` 是本设备后续写入使用的身份。`nodes` 保存所有字符节点，包括已删除的。`tombstones` 是墓碑集合，本章只记录“这个身份已删除”。填写骨架的三参数内部构造器。第 9 章再把墓碑升级为带删除见证的 Map，并填写四参数构造器。insert/delete/merge 的基础流程不调用 CausalStamp，先让正文编辑能独立完成。

`new RGA(replicaId)` 输入本设备身份，返回空正文状态。`replicaId()` 无输入，直接返回这个身份，方便检查后续写入归属。写入方法都返回新实例。修改前复制集合，不要改变旧快照。

## 3. A 在中间输入 X：实现 insert

**假设**

事情按这个顺序发生：

```text
① A 已收到 S 的 ab，此后没有收到其他修改
② A 的可见序列是 [a(1,S), b(2,S)]，用户要求 insert(1, 'X')
```

**问题**

下标 1 应转换成哪个锚点？插在开头或末尾时怎么办？

**解释**

1. 锚点取插入位置的左邻居。
2. 下标 1 的左邻居是下标 0 的 a。锚点是 a 的身份 (1,S)。
3. 下标 0 没有左邻居。锚点是 null，新节点挂到虚拟根下。
4. 末尾位置的左邻居是最后一个可见字符。

`insert(int index, char c)` 接收当前可见正文的位置和字符，返回插入后的新状态。允许 `index` 从 0 到当前长度，其他位置抛 `IndexOutOfBoundsException`。

把 TODO 拆成三段：

```text
visible = 按确定顺序读出的可见节点
校验 0 <= index <= visible.size()
parentId = index == 0 ? null : visible[index - 1].id

maximum = 当前 nodes 中最大的 timestamp，空状态取 0
id = NodeId(maximum + 1, replicaId)

复制 nodes，加入 Node(id, parentId, c)
返回新状态，沿用墓碑
```

用本节的具体值演算一遍：

```text
visible = [a(1,S), b(2,S)]
index = 1，校验通过（0 <= 1 <= 2）
parentId = 可见序列[0] 的身份 = (1,S)
maximum = max(1, 2) = 2
id = (3,A)
新节点 = Node(id=(3,A), parentId=(1,S), value='X')
```

插入后的节点链：

```text
虚拟根
└─ a (1,S)
   ├─ b (2,S)
   └─ X (3,A)
```

a 的子节点按身份升序是 [b(2,S), X(3,A)]。下一节的读取规则让新节点 X 先读，正文是 `aXb`，与要求一致。

编号来源有一条边界：取**所有现存节点**的最大编号，包括已删除节点，不能只看可见正文。例：状态里有已删除的 (5,B)，下次插入仍从 6 开始。合并后再插字，也接在已知最大编号之后。

这里用到了“按确定顺序读可见节点”的辅助方法。先按上面确定插入的输入和数据，再实现下一节的读取，最后回来连通 `insert`。

## 4. 把节点读成正文：实现 visibleNodes、text、size

**假设**

事情按这个顺序发生：

```text
① A、B 都收到 S 的 ab
② A 在 a 后插入 X，产生节点 X(3,A)，锚点是 (1,S)
③ B 不知道 ②，也在 a 后插入 Y，产生节点 Y(3,B)，锚点是 (1,S)
④ A、B 互相同步；两台设备都有 a、b、X、Y 四个节点
```

合并后的结构：

```text
虚拟根
└─ a (1,S)
   ├─ b (2,S)
   ├─ X (3,A)
   └─ Y (3,B)
```

**问题**

这些节点按什么顺序读？只按全部节点的编号排序够不够？

**解释**

先给结论：同一锚点下新节点先读；读完一个节点的整个分支，再读下一个兄弟。理由分三步：

1. 若兄弟按编号升序读，顺序是 a、b、X、Y，正文是 `abXY`。
2. b 排到了 X 前面。X 不在 a、b 中间，与 ② 的输入不符。
3. 约定同一锚点下的兄弟按身份降序访问。(3,B) 与 (3,A) 编号相同，设备 ID "B" 排在 "A" 后，所以 (3,B) 更大，Y 先读。
4. 降序只用于裁决并发顺序。它不声称 Y 在真实世界更晚写入。结果应是 `aYXb`。

还不能把所有节点直接排序。再看一个带分支的场景：

```text
① A 在 a 后输入 X，再在 X 后输入 1：X(3,A) 挂在 a 下，1(4,A) 挂在 X 下
② B 不知道 ①，在 a 后输入 Y，再在 Y 后输入 2：Y(3,B) 挂在 a 下，2(4,B) 挂在 Y 下
③ 合并后先读 Y，读完 Y 的整个分支（Y、2），再读 X 的分支（X、1），最后读 b
④ 结果是 aY2X1b
```

这种读法叫前序遍历：先读某个节点，再读完整个后代分支，然后才读下一个兄弟。

为复用读取规则，在类内实现辅助方法 `visibleNodes()`，以及负责压栈的 `pushChildren`。`visibleNodes()` 无输入，返回按这个规则排序、且排除墓碑的节点列表。列表保留身份信息，供插入、删除定位。`text()` 无输入，依次拼接这些节点的 `value`，返回字符串。`size()` 返回列表长度。

先建立“锚点 → 子节点列表”，再排序、遍历：

```text
children = 按 node.parentId 分组所有节点
每份兄弟列表按 NodeId 升序排序
把虚拟根的子节点依次压入栈
while 栈不为空:
    node = 出栈
    如果 node.id 不在墓碑里，将 node 加进 visible
    无论是否已删除，都把 node 的子节点依次压入栈
```

用本节假设的四个节点演算一遍。栈一列按“顶 → 底”书写：

| 步骤 | 动作 | 栈（顶→底） | 可见序列 |
| --- | --- | --- | --- |
| ① | 压入虚拟根的子节点 [a] | a | （空） |
| ② | 弹出 a；压入 a 的子节点 b、X、Y | Y，X，b | a |
| ③ | 弹出 Y；Y 没有子节点 | X，b | aY |
| ④ | 弹出 X；X 没有子节点 | b | aYX |
| ⑤ | 弹出 b；b 没有子节点 | （空） | aYXb |

**升序排序不等于升序访问**。参考实现的 `pushChildren` 从兄弟列表开头依次 `push`。栈后进先出。对 [b,X,Y] 依次压栈，先弹出 Y，再是 X，最后是 b。子节点又压到栈顶，所以会先读完整个分支。

把这个顺序写在纸上，再填 `pushChildren`。如果反过来压栈，两个副本可能仍然输出相同字符串，但本地“中间插入”的语义已经错了。

## 5. B 删除原来的 b：实现 delete

**假设**

事情按这个顺序发生：

```text
① A 已插入 X，未收到 B 的修改；A 看到 aXb，可见序列是 [a(1,S), X(3,A), b(2,S)]
② B 已插入 Y，未收到 A 的修改；B 看到 aYb，可见序列是 [a(1,S), Y(3,B), b(2,S)]
③ B 执行 delete(2)，删除自己看见的 b
④ 之后 A、B 同步
```

**问题**

同步后 A 怎样确定删的是原来的 b？能否直接把 b 节点从状态里移除？

**解释**

1. B 先把下标 2 转换成本地可见序列中的身份。
2. B 的可见序列下标 2 是 b，身份是 (2,S)。
3. B 记录“删除身份 (2,S)”，不记录“删除下标 2”。
4. A 收到后按身份找节点。(2,S) 在 A 的状态里就是原来的 b。
5. 同步的是删除身份。不要在 A 的新正文里重新执行下标删除。

`delete(int index)` 接收当前可见正文的下标，返回增加墓碑的新状态。允许 `0 <= index < size()`。空正文或越界删除应抛 `IndexOutOfBoundsException`。

核心算法：

```text
visible = visibleNodes()
校验下标
id = visible[index].id
复制墓碑，记下 id 已删除
返回新状态，保留 nodes
```

用 B 的具体值演算一遍：

```text
visible = [a(1,S), Y(3,B), b(2,S)]
index = 2，校验通过（0 <= 2 < 3）
id = (2,S)
墓碑集合：{} → {(2,S)}
nodes 不变：b 节点保留，只是不再输出
```

参考实现还给墓碑记录删除见证。本章先理解主线：删除以身份为目标，节点保留。第 9 章再补见证的含义。

为什么不能移除节点？再看一个场景：

```text
① 正文结构是 a → b → c，c 的锚点是 b
② 用户删除 b，期望看到 ac
```

1. 若从 `nodes` 移除 b，c 的锚点 (2,S) 指向不存在的节点。
2. 遍历时从 a 无法走到 c。c 会丢失。
3. 所以 b 留作墓碑锚点。
4. 读取时跳过 b 的输出，仍把 b 的子节点压栈。
5. c 留在原位置。正文是 `ac`。

## 6. 联网合并正文：实现 merge

**假设**

事情按这个顺序发生：

```text
① A 的状态：节点 a(1,S)、b(2,S)、X(3,A)，没有墓碑
② B 的状态：节点 a(1,S)、b(2,S)、Y(3,B)，墓碑记录 (2,S) 已删除
③ A 收到 B 的状态，执行 merge
```

**问题**

同一个 a 会收到两份，应该重复显示吗？一个身份若对应两个不同字符，又怎么办？

**解释**

`merge(RGA other)` 输入对方状态，返回合并后的新状态。`other` 为 null 时抛 `IllegalArgumentException`。后续本地写入继续用接收者的 `replicaId`。

先复制本地节点，再遍历对方节点：

```text
ID 不存在：加入整个节点
ID 已存在，节点三项相同：重复消息，保留一份
ID 已存在，但字符或锚点不同：抛异常，身份发生冲突
```

用本节的两个状态演算节点合并：

| 对方节点 | 本地是否已有 | 处理 |
| --- | --- | --- |
| a(1,S)，三项相同 | 已有 | 保留一份，不重复显示 |
| b(2,S)，三项相同 | 已有 | 保留一份 |
| Y(3,B) | 没有 | 加入 |

再合并墓碑。本章墓碑是 Set，取并集：{} ∪ {(2,S)} = {(2,S)}。任何一方已经删除的身份都继续删除。第 9 章升级为 Map 后，同一身份的多个删除见证再统一成确定选择。

不需要在合并时生成最终字符串，也不重算锚点。合并完成后让 `text()` 按相同遍历规则读取：

```text
nodes = {a(1,S), b(2,S), X(3,A), Y(3,B)}，墓碑 = {(2,S)}
a 的子节点按身份升序：[b(2,S), X(3,A), Y(3,B)]，出栈顺序是 Y、X、b
Y 不在墓碑 → 输出 Y
X 不在墓碑 → 输出 X
b 在墓碑 → 跳过输出；b 没有子节点
最终正文：aYX
```

X、Y 都保留，原来的 b 不输出。

合法输入必须保证锚点指向已知节点或虚拟根，结构无环。参考实现检查相同身份的内容冲突，但没有完整验证任意外部导入的缺失锚点或环。本章通过构造、插入和合并合法状态维持这些条件。

## 7. 同样的正文等于同样的状态吗：实现 equals

**假设**

两个状态当前都显示 `ac`：

```text
① 状态一：nodes 里仍保存被删除的 b 和它的墓碑；b 是 c 的锚点
② 状态二：nodes 里没有 b
```

**问题**

只比较 `text()` 能验证同步完成吗？

**解释**

1. 不能。
2. 字符身份、锚点和墓碑决定后续插入的位置和合并的结果。
3. 两个状态当前显示相同，后续行为仍可能不同。
4. 所以状态比较必须看 nodes 和墓碑，不能只看当前显示。

`equals(Object other)` 接收任意对象，返回它是否为 RGA 且 `nodes`、`tombstones` 都相等。`hashCode()` 使用同样两份数据。基础阶段墓碑是 Set，按已删除身份比较。第 9 章升级为 Map 后，见证也参与参考实现的比较。本地副本身份和修改进度不参与比较。

调试字符身份时，`NodeId.toString()` 无输入，返回编号和设备 ID 的描述。调试当前页面时，`RGA.toString()` 返回 `text()`。这些输出只便于观察，不代替状态比较。

因此测试既要比较合并后的状态，也要检查具体正文。两个状态一起读成错误的 `abXY`，仍可能相等，但没有完成“在 ab 中间插字”的任务。

## 8. 跑通一篇正文的完整操作

**假设**

事情按这个顺序发生：

```text
① 设备 S 写出 ab
② A、B 各用自己的身份加入，都收到 S 的状态
③ A 在中间插入 X
④ B 不知道 ③，也在中间插入 Y
⑤ A 收到 B 的状态，合并
⑥ B 删除自己看见的 b
⑦ A 再次收到 B 的状态，合并
```

每次编辑都保存返回的新状态。

**问题**

每行之后分别能看到哪些字符？合并是否保留两次输入并准确删除 b？

```java
RGA shared = new RGA("S").insert(0, 'a').insert(1, 'b');
RGA a = new RGA("A").merge(shared).insert(1, 'X'); // aXb
RGA b = new RGA("B").merge(shared).insert(1, 'Y'); // aYb
RGA joined = a.merge(b);                           // aYXb
b = b.delete(2);                                  // aY
joined = a.merge(b);                              // aYX
```

**解释**

逐行演算：

| 行 | 动作 | 节点与墓碑的变化 | 正文 |
| --- | --- | --- | --- |
| 1 | S：insert(0,'a')，insert(1,'b') | 加入 a(1,S)，锚点 null；加入 b(2,S)，锚点 (1,S) | ab |
| 2 | A：merge(shared)，insert(1,'X') | 加入 X(3,A)，锚点 (1,S) | aXb |
| 3 | B：merge(shared)，insert(1,'Y') | 加入 Y(3,B)，锚点 (1,S) | aYb |
| 4 | a.merge(b) | 学到 Y；a 的子节点出栈顺序 Y、X、b | aYXb |
| 5 | b.delete(2) | B 的可见序列 [a,Y,b]；下标 2 是 (2,S)；墓碑加入 (2,S) | aY |
| 6 | a.merge(b) | 学到墓碑 (2,S)；b 不输出 | aYX |

检查三个要点：

1. 初始字符用 S 的身份。新字符各用 A、B 的身份。删除命中 (2,S)，即原来的 b。
2. 新设备加入一份已有正文，应使用 `new RGA(myId).merge(sharedState)`。merge 保留调用方的身份，之后的新节点都带本地身份。
3. 不要拿同一个写入身份的状态分叉后各自插入不同字符。两边会生成相同身份，merge 时抛冲突异常。

标记为第 9 章的 `version()`、`tombstoneCount()`、`gc()` 暂时留到那里；本章测试不依赖这些方法。完成核心 TODO 后，对照 [完整参考 RGA.java](../RGA.java) 核对结构、排序与压栈，特别是墓碑节点仍遍历后代这一行。

字符身份的 `timestamp` 与 `version` 不是同一个编号。`timestamp` 由现存节点的最大编号推出。`version` 记录本设备插入和删除的修改进度。墓碑回收留到 [第 9 章](09-墓碑GC.md)。当前参考实现没有保留跨 GC、重启的完整编号高水位。GC 删除最大节点后再次插入，可能复用旧身份。这个边界尚未解决。
