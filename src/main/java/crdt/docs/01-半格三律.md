# 第 1 步：只添加标签时，怎样合并才可靠

[← 快速开始](00-快速开始.md) ｜ [目录](../README.md) ｜ [下一章：统计操作次数 →](02-计数器.md)

**上一步**：知道手机和电脑各保存一份笔记，合并不是直接覆盖。

**本课任务**：先只允许给笔记加标签，为合并订下共同约定。

**完成后**：能说明重复、换序、转发为什么不应改变结果。

**练习入口**：[CvRDT](../learnning/CvRDT.java)，这里是接口声明；具体实现从下一课开始。

## 1. 手机加旅行，电脑加工作

**假设**

从一篇尚未添加标签的笔记开始，手机 A 添加旅行，电脑 B 添加工作，此时分别是 `{旅行}`、`{工作}`。暂时不允许删除标签。

**问题**

同步后该有哪几个标签？覆盖或拼列表有什么问题？

**解释**

应该有旅行和工作。覆盖丢一份；拼列表可能在重发时出现两个工作。集合并集刚好得到双方已有标签，并自动去重。

```text
A：{旅行}     B：{工作}
合并：{旅行, 工作}
```

## 2. 同一条标签消息又来了

**假设**

电脑重复发来 `{工作}`；两边可能先收到对方、也可能先汇总到平板 C 再转发。C 另有 `{周末}`。

**问题**

重复、换序或换一种转发分组后，最终标签应该不同吗？

**解释**

不应不同。这给 merge 三条要求：

| 情况 | 要求 | 后文名称 |
|---|---|---|
| 同一状态再次合并 | 结果不变 | 幂等 |
| A 合 B、B 合 A | 信息结果相同 | 交换 |
| 先合 A/B、或先合 B/C | 最后结果相同 | 结合 |

三种要求就是三律。它们让网络次序不决定答案，但没有负责把消息送达。

## 3. 为不同部件定义共同入口

**假设**

操作统计要加次数，标题要保存文字，正文要插字；它们的本地修改各不相同，但都要汇总另一份状态。

**问题**

接口需要声明哪些方法，为什么只有 merge？

**解释**

共同需求只有“合并同类型状态并得到同类型结果”。因此接口只声明 merge，本地更新留给每个数据类型。

下面 T 表示具体类型。后面 GCounter 实现 `CvRDT<GCounter>`，输入、返回都固定为 GCounter，不会误把正文拿来与计数合并。

```java
public interface CvRDT<T extends CvRDT<T>> {
    T merge(T other);
}
```

接口已是框架，没有算法可填写。Java 只检查类型关系，不会替你证明三律。

## 4. 仅有三律，还缺什么

**假设**

A 添加旅行后，没有发给任何人就把内部记录清空；或者 A、B 永远不通信。

**问题**

并集符合三律，是否还能保证两边不丢数据？

**解释**

不能。更新不能随意忘掉必要证据，同步还得最终传播完整。后面删除标签时，会增加删除证据，而不是抹掉全部经历。

这里“更多”指保存了更多合并需要的信息，用户看到的值却可以变少。数学把这个信息关系叫偏序，把刚好汇总两边的操作叫 join；能够这样合并的结构叫半格。先理解并集例子，再记名字即可。

空状态不带信息，与任意状态合并都不影响对方，它叫底元素。

## 在练习里保留的约定

更新和 merge 返回新状态，不改输入。相等用 equals 判断复制信息，不比较对象地址；哪些字段参与比较，要由具体类型的语义决定。

只读视图、泛型内容不被外部偷偷修改，同样是保留旧快照所需的条件。接口纯声明可以先编译，下一章的测试再检验具体实现。

```bash
CRDT_BUILD=$(mktemp -d /tmp/crdt-contract.XXXXXX)
javac -encoding UTF-8 -d "$CRDT_BUILD" src/main/java/crdt/learnning/CvRDT.java
```
