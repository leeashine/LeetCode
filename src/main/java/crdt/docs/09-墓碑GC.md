# 第 9 步：墓碑 GC / 因果稳定 —— 让内存不无限膨胀

**目标**：第 5、6 步的墓碑、第 8 步的增量缓冲都是"只增不减"的。这一步在**不复活数据**的前提下把它们回收掉。

**大白话**：想删一个墓碑，必须先回答一个问题：**"是不是所有副本都已经知道这条记录死了？"**

```
副本 A 删了 x，墓碑 t 只在 A 手里。
如果 A 自作主张把 t 丢掉，然后和还没同步过的 B 合并：
  B 手里的 x 还活着 → t 消失 → x 复活 ❌

正确判据（因果稳定）：
  frontier = 所有副本 version 向量的逐分量最小值
  frontier 覆盖了"删除 x 的那次操作" → 人人可见 → 才能丢 t ✅
```

## 你要写的 API

```java
/** 因果时间戳：标识"某个副本的第 seq 次本地操作"。 */
public final class CausalStamp implements Comparable<CausalStamp> {
    public CausalStamp(String replicaId, long seq);
    public String replicaId();
    public long seq();
    public static CausalStamp min(CausalStamp left, CausalStamp right);
}

/** 稳定前沿：所有副本都已观察到的因果坐标。 */
public final class CausalStability {
    public static VersionVector frontier(List<VersionVector> observed);  // 逐分量取 min
    public static boolean covers(VersionVector frontier, CausalStamp stamp);
}

// ORSet / RGA 上新增
public VersionVector version();                        // 每次本地操作 +1，merge 取 max
public int tombstoneCount();
public ORSet<E> gc(VersionVector stableFrontier);      // ORSet
public RGA gc(VersionVector stableFrontier);           // RGA
```

## 算法要点

**1）每个墓碑要记住"是哪次操作删掉它的"**

```
remove(x) 时：
  version' = version.increment(replicaId)          // 本地操作计数 +1
  stamp    = new CausalStamp(replicaId, version'.get(replicaId))
  tombstones += {x 的 tag}  且  tombstoneStamps[tag] = stamp
```

多个副本并发删同一条记录时，**取 stamp 的较小者**（`CausalStamp.min`）——任意一个见证都成立，取 min 只是为了让各副本**确定性地**收敛到同一个选择。

**2）`gc(frontier)`：只回收被前沿覆盖的墓碑**

```java
if (CausalStability.covers(frontier, stamp)) { tombstones.remove(id); tombstoneStamps.remove(id); }
```

**3）RGA 额外限制：只能回收"死叶子"**

这是本项目实测出来的硬约束。RGA 的节点是别人的**父锚点**：

```
a → b → c → d → e → f      删除 b、c、d（中段）
text = "aef"

b/c/d 都是死的，但 d 是 e 的父节点。
如果把 d 从 nodes 里删掉，e 就得重新挂到 c 下并重新按时间戳排序
→ e、f 的位置会错乱 ❌
```

所以 `RGA.gc` 只删满足三个条件的节点：

1. 在 `tombstones` 里（已删除）
2. stamp 被稳定前沿覆盖（人人可见）
3. **它是叶子**（没有任何节点的 `parentId` 指向它）

并且**迭代到不动点**：删掉叶子 `f` 之后 `e` 变成叶子，同一轮继续删——所以 `"abcdef"` 删掉尾部三个字符后，一次 `gc` 就能收干净整条死链。

> **诚实的结论**：RGA 的墓碑 GC 只能回收"死叶子"。**中段删除的墓碑必须保留作为结构锚点。** 真正的内存回收要靠另一条路——**全量压实（compaction）**：所有副本在同一个稳定前沿上，把文档整体重建成一个新基线（新基线里没有墓碑）。这也是 Yjs 等真实实现的做法（它们通常把 GC 推迟到"文档快照/导出"时做）。

**4）GC 的取舍（必须知道）**

- GC 之后，各副本的**内部**墓碑集合不再逐字节相同（`equals` 可能为 false），但**可观察语义**（`elements()` / `text()` / `size()`）仍完全一致
- 与一个**还没 GC 的老副本**合并，墓碑会被带回来（GC 部分失效）——但**数据不会复活**，因为老副本手里的"记录 + 墓碑"是一起存在的，merge 时会一起回来
- 新副本加入会让前沿退回 0，GC 暂停。副本成员变更需要单独机制处理

## 硬性不变量

- [ ] **前沿未覆盖时，一个墓碑都不能收**：`gc(VersionVector.empty())` 必须什么都不删
- [ ] **GC 不改变可观察语义**：`elements()` / `text()` / `size()` 前后必须完全一致
- [ ] **不复活**：GC 后与未 GC 的老副本合并，被删除的元素/字符绝不能重新出现
- [ ] **`version` 与发送缓冲不参与 `equals`**（本地/因果元数据，不是被复制的值语义）
- [ ] RGA 只回收**叶子**墓碑；ORSet 无此限制（tag 之间没有结构依赖）

## 破坏性实验（实测结果）

1. 把 `gc` 的判据从 `CausalStability.covers(frontier, stamp)` 改成 `true`（"时间够久就回收"）：

```java
if (CausalStability.covers(frontier, tombstoneStamps.get(tag))) {   // 改坏它
if (true) {                                                        // 变成"无脑回收"
```

实测：**4 个测试挂掉**——

```
✗ ORSetTest#gcWithEmptyFrontierRemovesNothing
✗ ORSetTest#gcRemovesStableTombstonesOnly
✗ ORSetTest#tombstoneStampsStayInSyncWithTombstones
✗ TombstoneGcTest#orSetGcIsBlockedUntilEveryReplicaObservedTheDelete
```

这就是墓碑 GC 为什么必须建立在**因果稳定**上，而不是"等一个固定时间窗"：按时间窗回收，等于赌"所有副本都及时同步了"，赌输就是数据丢失或复活。

2. 把 `RGA.gc` 的"只删叶子"限制去掉（允许回收任意墓碑节点）：

```java
if (nodes.containsKey(entry.getKey()) && !childCounts.containsKey(entry.getKey())
        && CausalStability.covers(frontier, entry.getValue())) {   // 改坏它：去掉中间那个条件
```

实测：**5 个测试挂掉**，其中 `TombstoneGcTest#rgaGcCannotCollectTombstonesThatStillAnchorLiveText`
正是"文本顺序错乱"的那一个——它断言中段墓碑**必须**被保留。

## 自检问答

1. 为什么不能"删除超过 24 小时的墓碑"？（答：时间不等于因果。一个断网三天的副本还没见过那条墓碑，你丢掉它，数据就复活了。真实系统里的"GC 宽限期"只是**近似**，严格做法是因果稳定）
2. 为什么 ORSet 可以回收中段墓碑而 RGA 不行？（答：ORSet 的 tag 之间是**独立集合**，没有结构依赖；RGA 的节点是**树的锚点**，删掉会改变后代的位置）
