# 第 9 步：标签已经删了，什么时候才能忘掉删除记录？

[← 目录](../README.md) ｜ 上一步：[第 8 步 增量同步](08-delta-state.md) ｜ 下一步：[总结与自检](99-总结与自检.md)

**上一步**：笔记的操作次数与标签可以只发送待确认变化。确认发送后，标签墓碑仍然存在；正文中被删除的字符也可能仍占一个节点。

**本课任务**：判断删除是否已被规定成员共同收到，并在额外约束下做部分回收。

**练习入口**：先补 [VersionVector.of](../learnning/VersionVector.java)、[CausalStamp](../learnning/CausalStamp.java) 和 [CausalStability](../learnning/CausalStability.java)；再给第 5、6 章的 [ORSet](../learnning/ORSet.java) 与 [RGA](../learnning/RGA.java) 增强删除进度和回收能力。

**验收入口**：[GcLearningTest](../../../../test/java/crdt/learnning/GcLearningTest.java)。可见成果是：未收到删除的设备阻止回收；条件成立时，标签墓碑或正文死叶子减少，当前界面内容不变；你也能指出哪些旧信息仍会破坏回收后的结果。这不是一个完整的生产 GC 协议。

**阅读约定**：本章设备简记为 **A（手机）**、**B（电脑）**、**C（平板）**。添加标签会生成**票**：票 A1 表示“设备 A 的第 1 张票”；票序号只随添加增加，删除不增加。第 2 节定义**删除坐标**的写法 (A,2)，第 3 节定义**进度表**与**前沿表**的写法 {A=1,B=0}，先记住写法即可。

## 1. 手机删了“工作”，离线电脑还留着它

**假设**

事情按这个顺序发生：

```text
① A 添加标签“工作”，生成票 A1
② A 同步给 B，B 收到票 A1
③ A 删除“工作”：票 A1 成为墓碑，A 记住“票 A1 已被删除”
④ B 离线，没有收到这次删除；此刻 B 的屏幕上仍有“工作”
```

**问题**

A 的屏幕已经没有“工作”。A 能马上把“票 A1 已被删除”这条记录也丢掉吗？

**解释**

1. 不能。
2. 假设 A 丢掉了这条记录。
3. B 稍后再同步，会再带来票 A1。
4. A 没有证据判断票 A1 已被删除，“工作”会重新出现。
5. 这种现象叫数据复活。

墓碑不是为当前屏幕保存的。墓碑是为还可能到达的旧票保存的。等待固定时长也不能证明断网设备已收到删除。先明确成员和同步进度，再谈回收。

本节暂用普通 `ORSet` 的完整状态同步。第 8 章 `DeltaORSet` 没有 `version/gc`：它的 `ack()` 只清发送缓冲，不清墓碑，也不能证明所有设备已共同收到删除。

## 2. 两边都知道添加，却只有手机知道删除

**假设**

事情按这个顺序发生：

```text
① A 的第 1 次有效操作：添加“工作”，生成票 A1
② A 同步给 B，B 收到票 A1
③ A 的第 2 次有效操作：删除“工作”
④ B 离线，只收到到 A 的第 1 次操作
```

**删除坐标**记作 (设备, 序号)，表示“这台设备的第 n 次有效操作”。③ 的删除坐标是 (A,2)，类型名是 `CausalStamp`（部分代码注释叫它删除见证）。此刻：A 知道到 (A,2)；B 只知道到 (A,1)。

**问题**

两台设备都知道票 A1。这能证明两台设备都知道这次删除吗？应该检查哪个坐标？

**解释**

1. 不能。
2. 票 A1 标识“删的是哪次添加”。
3. 删除坐标 (A,2) 标识“是哪次操作删的”。
4. 回收要检查后者。

`CausalStamp` 保存设备身份和有效本地操作序号。序号不是毫秒时间，也不是添加票的序号。两种序号会不同，不能互相代用。用具体值走一遍：

```text
A 添加“工作”：票 A1；进度表 A 栏变为 1
A 删除“工作”：删除坐标 (A,2)；进度表 A 栏变为 2；票序号计数器仍是 1
A 再添加“旅行”：票 A2；进度表 A 栏变为 3
票 A2 的序号是 2，产生它的操作序号是 3。两种序号已经不同。
```

由此引出两个字段：

1. 每份状态保存一张第 4 章的进度表 `version`。
2. 每张墓碑关联一个删除坐标。

进度规则只有两条：

1. 只有实际改变状态的操作才增加本地进度。删除不存在的标签不改变状态，不增加进度。
2. 收到完整状态时，进度表逐设备取 max。结果表示已应用历史的并集。

## 3. 三台设备分别知道 A 的第 4、3、1 次操作

**假设**

规定成员是 A、B、C。**进度表**记作 {设备=次数,...}：{A=4,B=2} 表示“已完整应用 A 的前 4 次操作和 B 的前 2 次操作”；缺的栏按 0 算。三台设备已完整应用的历史如下：

```text
① A 的进度表：{A=4, B=2}
② B 的进度表：{A=3, B=2}
③ C 的进度表：{A=1}（C 还没收到过 B 的操作）
④ A 的第 2 次操作是一次删除
```

**问题**

A 的第 2 次删除，三台设备都收到了吗？“共同知道”的进度逐栏取 max 还是 min？

**解释**

1. 没有。C 只完整应用到 A 的第 1 次。
2. 共同进度逐栏取 min。缺一栏按 0，不能忽略。

逐栏演算：

```text
A 栏：min(4, 3, 1) = 1
B 栏：min(2, 2, 0) = 0    ← C 没有 B 栏，按 0
共同进度 = {A=1}（min 为 0 的栏不写入表）
```

这张共同进度表叫**稳定前沿**，本章记作前沿表。检查删除坐标 (A,2)：前沿表 A 栏是 1，1 < 2，所以这次删除不是人人都收到了。

注意“到第 n 次”的含义：它必须表示相关历史已经完整应用，不是碰巧收到第 n 号消息。完整状态同步满足这个含义：状态本身带着相关添加与删除。若改成有缺口的操作流，只取最大已收编号不足以证明完整应用。

现在从这张纸上的表开始编码，先不改 GC。前沿表只是一个判断输入。后面还要看旧消息和正文结构的条件。

## 4. 已经有一张表，怎样放进 VersionVector？

**假设**

事情按这个顺序发生：

```text
① 第 3 节的演算给出一张 Map<String,Long>，例如 {A=4,B=2}
② 第 4 章已经实现 get、asMap、merge、increment
```

**问题**

难道要反复调用 `increment`，才能把 4 放进向量吗？

**解释**

1. 不必。
2. 用 `VersionVector.of(map)`：它接收一张已计算的进度表，返回一个不可变向量。
3. `of` 不制造新操作，只负责构造表。

**本步实现**：沿用第 4 章的 `SortedMap<String,Long> counters` 字段与私有构造器，补 `of` 的 TODO。检查三条：身份非空；值非 null 且非负；值为 0 的项不写入，让 {A=0} 与空表表示同一个进度。复制输入。不要让调用者事后修改 map 就改掉已生成的向量。

<details>
<summary>VersionVector.of 的参考方法体</summary>

```java
if (counters == null) throw new IllegalArgumentException("counters must not be null");
SortedMap<String, Long> copy = new TreeMap<>();
for (Map.Entry<String, Long> entry : counters.entrySet()) {
    String id = entry.getKey();
    Long value = entry.getValue();
    if (id == null || id.isEmpty()) {
        throw new IllegalArgumentException("replicaId must not be empty");
    }
    if (value == null || value < 0) {
        throw new IllegalArgumentException("count must be nonnegative");
    }
    if (value > 0) copy.put(id, value);
}
return new VersionVector(copy);
```

构造器按第 4 章的方式保存只读表；0 不存，但 `get(id)` 仍返回 0。

</details>

## 5. 怎样把“删除发生在 A 的第 2 次”存下来？

**假设**

事情按这个顺序发生：

```text
① 删除坐标是 (A,2)，但目前只有两个分散的变量：身份 "A"、序号 2
② A 删除过票 A1，B 也删除过票 A1，两份状态各记下一个真实的删除坐标
③ 两份状态合并
```

**问题**

哪个对象负责保存 (A,2)？合并时两个真实删除坐标选谁？

**解释**

1. 用 `CausalStamp(replicaId,seq)` 把身份和序号绑在一起。
2. `replicaId()`、`seq()` 是读取入口。
3. 序号从 1 开始。没有第 0 次删除，所以构造时拒绝非正序号。

对②③：多个设备删除同一张已知票时，保留其中一个真实删除坐标即可。为了让各设备选得一致，补 `compareTo(other)`：先比序号，再比身份。`min(left,right)` 返回这个全序中较小的一个。用具体值走一遍：

```text
(A,2) 与 (B,3)：序号 2 < 3，选 (A,2)
(A,2) 与 (B,2)：序号相同，身份 "A" < "B"，选 (A,2)
```

此顺序只用于确定选择，不证明跨设备的因果先后。

**本步实现**：先定义两个 final 字段并补构造器，再补 getter、`equals/hashCode`。相同设备、相同序号才是相同坐标。

<details>
<summary>CausalStamp 的构造、比较与取见证</summary>

```java
// 构造器：字段为 private final String replicaId; private final long seq;
if (replicaId == null || replicaId.isEmpty() || seq <= 0) {
    throw new IllegalArgumentException("invalid causal stamp");
}
this.replicaId = replicaId;
this.seq = seq;

// compareTo 的方法体
if (other == null) throw new IllegalArgumentException("other must not be null");
int bySeq = Long.compare(seq, other.seq);
return bySeq != 0 ? bySeq : replicaId.compareTo(other.replicaId);

// min 的方法体
return left.compareTo(right) <= 0 ? left : right;
```

getter 直接返回对应字段；相等与哈希同时使用身份和序号。完整参考：[CausalStamp](../CausalStamp.java)。

</details>

## 6. 给进度表，怎样回答“删除大家都收到没”？

**假设**

事情按这个顺序发生：

```text
① 三台成员设备当前的共同进度是前沿表 {A=1}
② 待检查的删除坐标是 (A,2)
③ C 同步了 A 的历史，三台设备都知道到 A 的第 3 次操作
④ 前沿表推进到 {A=3}
```

**问题**

计算共同进度和检查一次删除，分别做哪件事？

**解释**

1. `frontier(observed)` 接收规定成员的进度表列表，返回逐栏取 min 的新向量。
2. `covers(frontier,stamp)` 接收前沿表和删除坐标，返回 boolean。

用①到④的值各算一遍：

```text
covers({A=1}, (A,2))：前沿表 A 栏 = 1，1 < 2 → false，不能回收
covers({A=3}, (A,2))：前沿表 A 栏 = 3，3 ≥ 2 → true，可以回收
```

**本步实现**：在 `CausalStability` 补这两个 TODO。列表为空时返回空向量，表示没有可确认的共同历史。null 输入拒绝。收集各表的设备键，逐栏取 min；`get` 负责让缺项为 0。最后调用刚补好的 `VersionVector.of`。

<details>
<summary>frontier 与 covers 的参考方法体</summary>

```java
// frontier
if (observed == null) throw new IllegalArgumentException("observed must not be null");
if (observed.isEmpty()) return VersionVector.empty();
Set<String> keys = new TreeSet<>();
for (VersionVector version : observed) {
    if (version == null) throw new IllegalArgumentException("null version");
    keys.addAll(version.asMap().keySet());
}
Map<String, Long> minimum = new TreeMap<>();
for (String key : keys) {
    long value = Long.MAX_VALUE;
    for (VersionVector version : observed) value = Math.min(value, version.get(key));
    if (value > 0) minimum.put(key, value);
}
return VersionVector.of(minimum);

// covers
if (frontier == null || stamp == null) throw new IllegalArgumentException("null input");
return frontier.get(stamp.replicaId()) >= stamp.seq();
```

</details>

## 7. 判断做完了，给标签加上部分回收能力

**假设**

事情按这个顺序发生：

```text
① A 添加“工作”：票 A1；进度表 {A=1}
② A 删除“工作”：墓碑 A1，删除坐标 (A,2)；进度表 {A=2}
③ B 仍为空：进度表是空表
④ B 收到 A 删除后的完整状态：B 的进度表变为 {A=2}
⑤ 用两台设备的进度表再算一次前沿，并各做一次 gc
```

**问题**

怎样观察回收是否被挡住？删除坐标应该在哪一步写入？

**解释**

这才进入 `ORSet` 的增强。它不是第 5 章基础增删合并的先决条件。先加两个字段：`VersionVector version` 和 `Map<Tag,CausalStamp> tombstoneStamps`。填写六参数内部构造器，让每次更新返回增强状态。空集合的进度表初始化为空表。

注意一个边界：基础阶段已保存的墓碑没有删除坐标。不能凭空猜它是哪次删除。练习从本章的新空状态开始，生成带删除坐标的历史。迁移旧状态需要另外设计基线协议。

各方法的进度规则：

1. `version()` 输出当前已应用进度；`tombstoneCount()` 输出墓碑票数量，不是隐藏标签数量。
2. `add` 总是有效操作：每次添加生成新票，本地进度加一。
3. `remove` 只在元素有已知票时有效：先加进度，用新序号创建删除坐标，关联到这次删除的每张票。删除不存在的标签不改变状态。
4. `merge` 逐栏取 max 合进度；同票的多个删除坐标用 `CausalStamp.min` 统一。

然后补 `gc(stableFrontier)`：输入前沿表，输出回收后的新集合。检查每张墓碑的删除坐标是否被覆盖；被覆盖的，才从墓碑集合和坐标表移除。存活票、进度表、身份和添加序号不改变，界面标签也不改变。null 前沿拒绝，空前沿不回收。

把①到⑤代进去走一遍：

```text
③ 之后：前沿 = min({A=2}, {}) → A 栏为 0 → 空前沿
   covers(空前沿, (A,2))：A 栏 0 < 2 → false → gc 不回收，tombstoneCount() 仍为 1
④ 之后：B 的进度表 = {A=2}
⑤ 前沿 = min({A=2}, {A=2}) = {A=2}
   covers({A=2}, (A,2))：2 ≥ 2 → true → gc 回收墓碑 A1，tombstoneCount() 变为 0
```

<details>
<summary>标签增强的推导结果与可见输出</summary>

```text
A add("工作")：添加票 A1；version[A] = 1
A remove("工作")：墓碑 A1；见证 (A,2)；version[A] = 2
B 为空：version[A] = 0；frontier[A] = 0；gc 后墓碑仍为 1
B merge(A)：version[A] = 2；frontier[A] = 2；gc 后墓碑为 0
```

实现时复制墓碑与见证表，遍历墓碑，`covers(frontier, stamp)` 为 true 才同时移除两处记录。不要把添加票的序号当成删除见证。完整参考：[ORSet](../ORSet.java)。

</details>

## 8. 所有人收到删除，删除前旧快照又来了

**假设**

事情按这个顺序发生：

```text
① A 添加“工作”，同步给 B
② A 删除“工作”，同步给 B；此刻两台设备都已收到删除 (A,2)
③ 前沿表覆盖 (A,2)，A 回收了墓碑
④ 一份旧快照晚到：它只有添加、没有删除，来自备份或网络队列
```

**问题**

刚计算过稳定前沿，当前 `merge` 就能挡住旧快照吗？

**解释**

1. 不能。
2. 当前 `ORSet.merge` 不按回收前沿过滤旧添加。
3. 墓碑已被回收，删除证据已经丢掉。
4. 旧快照带来票 A1，没有墓碑剔除它，“工作”复活。

<details>
<summary>用已有方法观察当前边界</summary>

```java
ORSet<String> old = ORSet.<String>empty("A").add("工作");
ORSet<String> deleted = old.remove("工作");
ORSet<String> peer = ORSet.<String>empty("B").merge(deleted);
VersionVector stable = CausalStability.frontier(
        java.util.Arrays.asList(deleted.version(), peer.version()));
ORSet<String> collected = deleted.gc(stable);
System.out.println(collected.merge(old).contains("工作"));  // true，复活
System.out.println(collected.merge(peer).contains("工作")); // false，peer 带删除证据
```

</details>

对照上面代码的两个输出：

```text
collected.merge(old)：collected 的墓碑为空；old 带来票 A1 → 无墓碑剔除 → 复活（true）
collected.merge(peer)：peer 仍带墓碑 A1 → 票 A1 被剔除 → 不复活（false）
```

因此本章的部分回收实验需要额外约束：

1. 成员固定。
2. 删除前的快照和消息不能再次进入同步。
3. 可同步的成员已经完整应用删除。

尚未 GC、但已收到删除的副本仍带墓碑。与它合并不会复活，但会把墓碑带回来，需要再次 GC。

完整协议还需要消息屏障、有效基线或可拒绝旧历史的摘要。只有前沿表不足以保证任意旧消息都安全。不要把参考类的“安全回收”注释当作这些机制已经实现。

## 9. 正文删了 b，c 仍挂在 b 后面

**假设**

事情按这个顺序发生：

```text
① 正文依次插入 a、b、c：b 是 c 的父节点，结构是 a → b → c
② 删除 b：b 成为墓碑，显示 ac
③ 所有成员都已收到这次删除：删除坐标被前沿表覆盖
```

**问题**

能像标签墓碑一样，直接移除 b 的节点吗？

**解释**

1. 不能。
2. b 仍是 c 的父节点。移除 b 后，c 失去父节点。
3. 把 c 改挂到祖父，会改变按父节点确定的兄弟排序。
4. 删除稳定只说明删除已被所有成员收到。它不说明这个节点已没有结构用途。

实现升级分四步：

1. 第 6 章只存删除 ID 的 Set，本章升级为 `Map<NodeId,CausalStamp>`，并增加 `version`。填写四参数内部构造器，让插入、删除与合并返回增强状态。遍历改用 `containsKey(id)` 判断是否已删除。
2. 给 `RGA` 增加 `version()`、`tombstoneCount()`。插入、删除各增加一次有效本地进度；删除用新进度生成删除坐标。
3. 合并时逐栏取 max 合进度；同节点的多个删除坐标用 `CausalStamp.min` 确定选择。
4. 练习从新基线生成删除坐标，不为旧 Set 里的删除猜造编号。

再补 `gc(frontier)`：返回新正文。只回收已被前沿覆盖、且没有任何子节点的已删除节点。这种节点叫**死叶子**。中间锚点必须保留。用尾部 `d → e → f` 都已删除的例子走一遍：

```text
回收前：d → e → f，三个节点都已删除，删除坐标都被前沿表覆盖
第 1 步：f 没有子节点 → 回收 f
第 2 步：e 的子节点只有 f，f 已移除 → e 成为叶子 → 回收 e
第 3 步：d 的子节点只有 e，e 已移除 → d 成为叶子 → 回收 d
```

<details>
<summary>RGA 部分回收的实现顺序</summary>

```text
1. 根据所有节点统计每个父节点有多少子节点，含已删除子节点。
2. 将“有节点、无子节点、删除见证被覆盖”的 ID 放入队列。
3. 取出一个 ID，同时移除该节点与墓碑。
4. 父节点子数减一；减到 0，且父节点也已删除并稳定，再把父节点入队。
5. 队列空时返回新 RGA，version 保持原值。
```

不要只数可见子节点。完整参考：[RGA](../RGA.java) 的 `gc`。回收前后 `text()/size()` 应一致，但内部状态和 `equals` 可能不同。

</details>

## 10. 回收后继续写，或者新设备从旧备份加入

**假设**

事情按这个顺序发生：

```text
① RGA 回收了时间戳最大的尾部节点：时间戳 4 被回收，现存最大时间戳变为 3
② 同一设备接着插入一个新字符
③ 另一边，一台新设备从删除前的旧备份启动，带旧身份加入
```

**问题**

② 会复用已发出的 ID 吗？③ 把共同前沿退回 0，能补救已经回收的删除吗？

**解释**

先回答②：

1. 当前 RGA 用现存节点的最大时间戳加一分配 ID。
2. 回收后，新插入会再得到时间戳 4：

```text
回收前：节点时间戳 1(a)、2(b)、3(c)、4(d)，d 已删除且稳定
回收后：d 被移除，现存最大时间戳 = 3
下一次插入：新节点时间戳 = 3 + 1 = 4，与已回收的 d 相同
```

3. 与还记得旧节点的副本合并时，结果有两种：同 ID 不同内容的节点让合并抛 `IllegalArgumentException`；或新节点被旧墓碑当成已删除。
4. 要避免复用，需要跨 GC、跨重启保留不倒退的分配高水位，或使用不会重用的身份机制。当前实现没有补齐。

再回答③：

1. 前沿退回 0 只能阻止以后的回收。
2. 它不能恢复已经丢掉的墓碑。
3. 新成员要按有效基线加入；旧消息和旧身份也要遵守切换规则。
4. 只把可见正文复制成新字符串，不定义基线和旧消息拒绝规则，不能称为安全压实。

最后明确本章边界。GC 移除了复制信息，已经超出此前“信息只增长”的证明条件。本章验收的是共同收到的判断、受约束的部分回收与可见边界。本章不证明 GC 后任意持续写入、成员变化或历史恢复都正确。
