# 第 9 步：标签已经删了，什么时候才能忘掉删除记录？

[← 目录](../README.md) ｜ 上一步：[第 8 步 增量同步](08-delta-state.md) ｜ 下一步：[总结与自检](99-总结与自检.md)

上章已经能让笔记的操作次数与标签只发送待确认变化。但确认发送后，标签墓碑仍然存在；正文中被删除的字符也可能仍占一个节点。

本章任务是：**判断删除是否已经被规定成员共同收到，并学习在额外约束下部分回收。** 先补 [VersionVector.of](../learnning/VersionVector.java)、[CausalStamp](../learnning/CausalStamp.java) 和 [CausalStability](../learnning/CausalStability.java)；再给第 5、6 章的 [ORSet](../learnning/ORSet.java) 与 [RGA](../learnning/RGA.java) 增强删除进度和回收能力。

验收入口是 [GcLearningTest](../../../../test/java/crdt/learnning/GcLearningTest.java)。可见成果是：未收到删除的设备阻止回收；条件成立时标签墓碑或正文死叶子减少，当前界面内容不变；你也能指出哪些旧信息仍会破坏回收后的结果。这不是一个完整的生产 GC 协议。

## 1. 手机删了“工作”，离线电脑还留着它

**假设**：A 添加标签“工作”，票是 A1，并同步给 B。后来 A 删除这张票，B 离线没收到删除。

**问题**：A 的屏幕已经没有“工作”，能马上把“删除 A1”的记录也丢掉吗？

**解释**：不能。B 再带 A1 来同步时，A 已没有证据判断它被删过，“工作”会重新出现。这叫数据复活。

墓碑不是为了当前屏幕，而是为了还可能来的旧票。等一天也不能证明断网三天的设备收到了删除。先明确成员和同步进度，再谈回收。

这里暂用普通 `ORSet` 的完整状态同步。第 8 章 `DeltaORSet` 没有 `version/gc`；它的 `ack()` 清发送缓冲，不会清墓碑，也不能拿来证明所有设备已经共同收到删除。

## 2. 两边都知道添加，却只有手机知道删除

**假设**：A 的第 1 次有效操作添加“工作”，第 2 次有效操作删除它。B 只收到第 1 次。

**问题**：大家都知道 A1，能证明大家知道删除了吗？应该检查哪个编号？

**解释**：不能。添加票 A1 标识“删的是谁”；另一个坐标 `(A,2)` 标识“是哪次操作删的”。回收要检查后者。

删除坐标叫 `CausalStamp`。它保存设备身份和有效本地操作序号，不是毫秒时间，也不是添加票序号。随后再添加标签，票序号与操作序号更可能不同，不能互相代用。

由这个问题引出字段：给每份状态保留一张第 4 章的进度表 `version`；给每张墓碑关联删除坐标。只有实际改变状态的操作才增加本地进度；删除不存在的标签不增加。收到完整状态时，进度逐设备取 max，表示已应用的历史并集。

## 3. 三台设备分别知道 A 的第 4、3、1 次操作

**假设**：规定成员是 A、B、C，已完整应用的历史如下。

```text
A 的记录：A 到 4，B 到 2
B 的记录：A 到 3，B 到 2
C 的记录：A 到 1，B 尚未见过
```

**问题**：A 的第 2 次删除，大家都收到了吗？“共同知道”的记录取 max 还是 min？

**解释**：没有，C 只到第 1 次。共同进度只能是 `A=1，B=0`，每栏取最小值；缺一栏按 0，不能忽略。

共同进度叫**稳定前沿**。这里“到第 n 次”必须表示相关历史已经完整应用，不是碰巧收到第 n 号消息。在完整状态同步例子中，这份状态带着相关添加与删除；若改成有缺口的操作流，只取最大已收编号不足以证明完整应用。

现在从这张纸上的表开始编码，不先改 GC。前沿只是一个判断输入，后面还要看旧消息和正文结构的条件。

## 4. 已经有一张表，怎样放进 VersionVector？

**假设**：你手上是 `Map<String,Long>`，例如 `{A=4,B=2}`，第 4 章已经实现 `get/asMap/merge` 等方法。

**问题**：难道要反复调用 `increment` 才能把 4 放进去？

**解释**：不必。需要 `VersionVector.of(map)`：接一张已计算的进度表，返回一个不可变向量。它不制造新操作，只负责构造表。

**本步实现**：沿用第 4 章的 `SortedMap<String,Long> counters` 字段与私有构造器；补 `of` 的 TODO。检查身份非空、值非 null 且非负；丢掉值为 0 的项，让 `{A=0}` 与空表表示同一个进度。复制输入，不能让调用者后来修改 map 就改掉已经生成的向量。

<details>
<summary>VersionVector.of 的参考方法体</summary>

```java
if (counters == null) throw new IllegalArgumentException("counters must not be null");
SortedMap<String, Long> copy = new TreeMap<>();
for (Map.Entry<String, Long> entry : counters.entrySet()) {
    String id = entry.getKey();
    Long value = entry.getValue();
    if (id == null || id.isEmpty()) {
        throw new IllegalArgumentException("replicaId must not be empty");
    }
    if (value == null || value < 0) {
        throw new IllegalArgumentException("count must be nonnegative");
    }
    if (value > 0) copy.put(id, value);
}
return new VersionVector(copy);
```

构造器按第 4 章的方式保存只读表；0 不存，但 `get(id)` 仍返回 0。

</details>

## 5. 怎样把“删除发生在 A 的第 2 次”存下来？

**假设**：你知道删除坐标是 `(A,2)`，但目前只有两个分散的变量。

**问题**：哪个对象负责保存它？两份状态各记了不同的真实删除见证，合并选谁？

**解释**：用 `CausalStamp(replicaId,seq)` 把两项绑在一起。`replicaId()`、`seq()` 是读取入口，输出身份和正序号；没有第 0 次删除，所以构造时拒绝非正序号。

**本步实现**：先定义两个 final 字段并补构造器，再补 getter、`equals/hashCode`。相同设备、相同序号才是相同坐标。

若多个设备删除了同一张已知票，可以保留其中一个真实删除见证。为了让各设备选得一致，补 `compareTo(other)`：先比序号，再比身份；`min(left,right)` 返回这个全序中较小的那个。此顺序只用于确定选择，**不证明跨设备的因果先后**。

<details>
<summary>CausalStamp 的构造、比较与取见证</summary>

```java
// 构造器：字段为 private final String replicaId; private final long seq;
if (replicaId == null || replicaId.isEmpty() || seq <= 0) {
    throw new IllegalArgumentException("invalid causal stamp");
}
this.replicaId = replicaId;
this.seq = seq;

// compareTo 的方法体
if (other == null) throw new IllegalArgumentException("other must not be null");
int bySeq = Long.compare(seq, other.seq);
return bySeq != 0 ? bySeq : replicaId.compareTo(other.replicaId);

// min 的方法体
return left.compareTo(right) <= 0 ? left : right;
```

getter 直接返回对应字段；相等与哈希同时使用身份和序号。完整参考：[CausalStamp](../CausalStamp.java)。

</details>

## 6. 给进度表，怎样回答“删除大家都收到没”？

**假设**：前沿表已是 `{A=1}`，待检查的是 `(A,2)`；随后 C 同步了，前沿推进到 `{A=3}`。

**问题**：计算共同进度和检查一个删除，应分别做哪件事？

**解释**：`frontier(observed)` 接规定成员的进度表列表，返回逐栏 min 的新向量；`covers(frontier,stamp)` 接前沿与删除坐标，返回 boolean。第一次 false，第二次 true。

**本步实现**：在 `CausalStability` 补这两个 TODO。列表为空时返回空向量，表示没有可确认的共同历史；null 输入拒绝。收集各表的设备键，再逐栏取 min，`get` 负责缺项为 0，最后调用刚补好的 `VersionVector.of`。

<details>
<summary>frontier 与 covers 的参考方法体</summary>

```java
// frontier
if (observed == null) throw new IllegalArgumentException("observed must not be null");
if (observed.isEmpty()) return VersionVector.empty();
Set<String> keys = new TreeSet<>();
for (VersionVector version : observed) {
    if (version == null) throw new IllegalArgumentException("null version");
    keys.addAll(version.asMap().keySet());
}
Map<String, Long> minimum = new TreeMap<>();
for (String key : keys) {
    long value = Long.MAX_VALUE;
    for (VersionVector version : observed) value = Math.min(value, version.get(key));
    if (value > 0) minimum.put(key, value);
}
return VersionVector.of(minimum);

// covers
if (frontier == null || stamp == null) throw new IllegalArgumentException("null input");
return frontier.get(stamp.replicaId()) >= stamp.seq();
```

</details>

## 7. 判断做完了，给标签加上部分回收能力

**假设**：A 添加再删除“工作”，B 仍为空；等 B 收到 A 删除后的完整状态，再计算一次前沿。

**问题**：怎样观察回收是否被挡住？删除见证应该在哪一步写入？

**解释**：这才进入 `ORSet` 的增强，不是第 5 章基础增删合并的先决条件。先加 `VersionVector version` 和 `Map<Tag,CausalStamp> tombstoneStamps`，填写六参数内部构造器并让更新返回增强状态；空集合初始化为空表。基础阶段已保留的墓碑没有见证，不能凭空猜是哪次删除：练习从本章的新空状态开始生成带见证历史；迁移旧状态须另设计基线协议。

`version()` 输出当前已应用进度；`tombstoneCount()` 输出墓碑票数量，不是隐藏标签数量。`add` 有效时增加本地进度；`remove` 有已知票时先增加进度，以新序号创建删除见证，关联到这次删除的每张票。`merge` 逐分量 max 合进度，同票的多个删除见证用 `CausalStamp.min` 统一。

然后补 `gc(stableFrontier)`：输入前沿，输出回收后的新集合。检查每张墓碑的删除见证是否被覆盖；覆盖的才从墓碑集合和见证表移除。存活票、版本表、身份及添加序号不改变，界面标签也不改变。null 前沿拒绝，空前沿不回收。

<details>
<summary>标签增强的推导结果与可见输出</summary>

```text
A add("工作")：添加票 A1；version[A] = 1
A remove("工作")：墓碑 A1；见证 (A,2)；version[A] = 2
B 为空：version[A] = 0；frontier[A] = 0；gc 后墓碑仍为 1
B merge(A)：version[A] = 2；frontier[A] = 2；gc 后墓碑为 0
```

实现时复制墓碑与见证表，遍历墓碑，`covers(frontier, stamp)` 为 true 才同时移除两处记录。不要把添加票的序号当成删除见证。完整参考：[ORSet](../ORSet.java)。

</details>

## 8. 所有人收到删除，删除前旧快照又来了

**假设**：A、B 都已收到删除，A 回收了墓碑；备份或网络队列却留着一份只有添加、没有删除的旧快照。

**问题**：刚计算过稳定前沿，当前 `merge` 就能挡住旧票吗？

**解释**：不能。当前 `ORSet.merge` 没有依据回收前沿过滤旧添加，删除证据又被丢掉，旧标签会复活。

<details>
<summary>用已有方法观察当前边界</summary>

```java
ORSet<String> old = ORSet.<String>empty("A").add("工作");
ORSet<String> deleted = old.remove("工作");
ORSet<String> peer = ORSet.<String>empty("B").merge(deleted);
VersionVector stable = CausalStability.frontier(
        java.util.Arrays.asList(deleted.version(), peer.version()));
ORSet<String> collected = deleted.gc(stable);
System.out.println(collected.merge(old).contains("工作"));  // true，复活
System.out.println(collected.merge(peer).contains("工作")); // false，peer 带删除证据
```

</details>

因此本章部分回收实验需要额外约束：成员固定，删除前的快照和消息不能再次进入同步；可同步的成员已经完整应用删除。尚未 GC、但知道删除的副本仍带墓碑，合并不会复活，却可能把墓碑带回来。

完整协议还需消息屏障、有效基线或可拒绝旧历史的摘要。仅前沿不足以保证任意旧消息都安全；不要把参考类的“安全回收”注释当作实现了这些额外机制。

## 9. 正文删了 b，c 仍挂在 b 后面

**假设**：正文结构是 `a → b → c`，删除 b 后显示 `ac`；大家都已收到这次删除。

**问题**：能像标签墓碑一样，直接把 b 节点移除吗？

**解释**：不能。b 仍是 c 的锚点，移除后 c 失去父节点；重新挂到祖父又可能改变兄弟排序。删除稳定，只说明删除已被收到，不说明结构身份已没用。

第 6 章只存删除 ID 的 Set，本章升级为 `Map<NodeId,CausalStamp>` 并增加 `version`。填写四参数内部构造器，让插入、删除与合并保存增强状态；遍历改用 `containsKey(id)` 判断是否删除。练习从新基线生成见证，不为旧 Set 里的删除猜造编号。

给 `RGA` 增加 `version()`、`tombstoneCount()`，以及“节点 ID → 删除见证”的墓碑表；插入、删除各增加一次有效本地进度，删除用新进度生成见证。合并节点和删除见证时，也逐栏 max 合版本、确定选择同节点的见证。

再补 `gc(frontier)`：返回新正文，只回收已被前沿覆盖、且没有任何子节点的已删除节点，也叫**死叶子**。尾部 `d → e → f` 都已删除时，先收 f，e 成为叶子，再收 e，最后收 d。中间锚点必须保留。

<details>
<summary>RGA 部分回收的实现顺序</summary>

```text
1. 根据所有节点统计每个父节点有多少子节点，含已删除子节点。
2. 将“有节点、无子节点、删除见证被覆盖”的 ID 放入队列。
3. 取出一个 ID，同时移除该节点与墓碑。
4. 父节点子数减一；减到 0，且父节点也已删除并稳定，再把父节点入队。
5. 队列空时返回新 RGA，version 保持原值。
```

不要只数可见子节点。完整参考：[RGA](../RGA.java) 的 `gc`。回收前后 `text()/size()` 应一致，但内部状态和 `equals` 可能不同。

</details>

## 10. 回收后继续写，或者新设备从旧备份加入

**假设**：RGA 回收了时间戳最大的尾部节点，接着在同一设备插入；另一边，新设备从删除前备份启动。

**问题**：前者会复用 ID 吗？后者把共同前沿退回 0，能补救已经回收的删除吗？

**解释**：当前 RGA 用现存节点最大时间戳加一分配 ID，GC 后可能复用已发出的 ID，与旧节点合并会冲突或被旧墓碑误删。需要跨 GC、重启保留不倒退的分配高水位，或使用不会重用的身份机制；当前实现没有补齐。

前沿退回 0 只能阻止未来回收，不能恢复过去丢掉的墓碑。新成员需要按有效基线加入，旧消息和旧身份也要遵守切换规则。只把可见正文复制成新字符串，未定义基线和旧消息拒绝规则，不能称为安全压实。

GC 移除复制信息，已经超出此前“信息只增长”的证明条件。本章验收的是共同收到的判断、受约束的部分回收与可见边界，不证明 GC 后任意持续写入、成员变化或历史恢复都正确。
