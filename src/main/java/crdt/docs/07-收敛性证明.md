# 第 7 步：收敛性证明 —— 用恶劣网络验证前 6 步

**目标**：写一个测试，在**丢包 35% + 重复投递 + 任意乱序**的仿真网络里，证明所有副本必然收敛。

**大白话**：前面 6 步都靠"三律"推理出来的。但推理会出错，所以要**真的跑一遍**。

仿真注入三种恶劣行为：

| 恶劣行为 | 仿真做法 | 对应真实世界 |
|---|---|---|
| 乱序 | 副本之间任意顺序、任意方向同步 | 消息走不同链路 |
| 重复 | 同一条状态连续 merge 两次 | 至少一次投递（at-least-once） |
| 丢失 | 35% 的同步直接跳过 | 网络抖动、进程重启 |

**断言只有一句话**：所有副本两两 `equals`。

## 你要写的 API（测试骨架）

```java
private static <T extends CvRDT<T>> List<T> run(
        String name, Supplier<T> factory, Op<T> op, long seed) {
    // 1. 阶段一：各副本独立乱写 60 次（必然分叉）
    // 2. 阶段二：40 轮随机点对点反熵，带丢包(35%)和重复投递(40%)
    // 3. 断言：所有副本 equals
}
```

## 硬性要求

- [ ] 用**固定种子**的 `Random`（可复现；失败时能精确重放）
- [ ] **多个种子**（本项目每个类型跑 25 个种子）——单种子容易碰巧通过
- [ ] 除了"收敛"，每个类型还要断言一个**语义性质**，防止"大家一起收敛到同一个错误值"这种假通过：

| 类型 | 语义性质 |
|---|---|
| `GCounter` | 收敛后的 `value()` 等于所有副本累计操作之和 |
| `PNCounter` | 收敛后的 `value()` 等于净值 |
| `LWWRegister` | 保留的时间戳等于所有写里的最大时间戳 |
| `MVRegister` | 收敛后非空 |
| `ORSet` | 元素集合非空 |
| `RGA` | 可见长度 = 插入次数 − 删除次数；且各副本 `text()` 相同 |

- [ ] 定律测试里，**交换律必须对每一对状态都验**（本项目就因为这个漏洞放过了一个真实 bug，见第 3 步的踩坑记录）

## 动手实验（前两条是实测结果，第三条留给你）

1. 把丢包率从 `0.35` 调到 `0.9` —— **实测仍然 `OK (100 tests)`**。丢包只影响"需要多少轮"，不影响"最终能不能收敛"。
2. 把 `GOSSIP_ROUNDS` 从 40 降到 **3** —— **实测仍然 `OK (100 tests)`**。这个反直觉的结果值得记住：每轮都是全互联两两 merge，3 轮已经足够覆盖 5 个副本的**传播直径**。**反熵需要的轮数取决于拓扑直径，而不是副本数量。**
3. 把 `GOSSIP_ROUNDS` 改成 **0**（完全不做反熵）—— **实测 6 个收敛测试全挂**：

```
✗ ConvergenceTest#gCounterConverges
✗ ConvergenceTest#pnCounterConverges
✗ ConvergenceTest#mvRegisterConverges
✗ ConvergenceTest#lwwRegisterConvergesToHighestTimestamp
✗ ConvergenceTest#orSetConverges
✗ ConvergenceTest#rgaConverges
```

**"最终一致"里的"最终"，指的是"真的同步过之后"。** CRDT 不会自己传播，它只保证传播的时序怎么乱都不出错。

## 自检问答

1. 为什么"收敛"不需要任何重传/去重逻辑？（答：因为 merge 幂等 + 交换，重传和重复到达都不改变结果。CRDT 把可靠性推给了"最终一定会同步一次"这个弱假设）
2. 这个测试能证明什么、不能证明什么？（答：能证明 merge 满足三律；**不能**证明语义符合用户意图——那是第 6 步那个破坏性实验的教训）
