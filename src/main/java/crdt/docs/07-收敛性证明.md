**阅读约定**：本章有两台主要设备：手机和电脑，简记为 **A（手机）**、**B（电脑）**。另有一台设备 **S**，只负责写出初始内容。记号沿用前面章节：**A2/B3** 表示计数器状态：A 的分量是 2，B 的分量是 3，总数是各分量之和（第 2 章）；票 **A1** 表示 A 发出的第 1 张添加票（第 5 章）；坐标 **(2,S)** 表示 S 写出的第 2 个字符（第 6 章）。本章把消息事件统一成四个词：送达（消息到达对方，对方执行 merge）、丢失（消息没有到达）、重发（同一条消息再送一次）、晚到（旧状态在较晚时刻才送达）。

## 1. 大家都空了，也算一致吗

**假设**

事情按这个顺序发生：

```text
① 手机添加标签“旅行”。手机持有 {旅行}
② 手机的状态送达电脑。电脑的 merge 有错误：无论收到什么，都返回空集合。电脑变成 {}
③ 电脑的状态送达手机。手机的 merge 是同一份错误实现。手机也变成 {}
④ 对两个状态执行 assertEquals：两边都是 {}，断言通过
```

**问题**

只断言两边相等，能发现“旅行”被丢了吗？

**解释**

1. 不能。两边都是空集合，相等断言通过。
2. 相等只说明“两边一样”，不说明“一样得对”。
3. 必须先另算期望的可见结果，再断言它。
4. 本例的期望是 {旅行}。两边都是 {}，与期望不符，错误被发现。

本章三个用例的期望结果都要先算出来：

| 用例 | 期望的可见结果 | 依据 |
| --- | --- | --- |
| 计数器 | value() = 7 | 手机记 3 次，电脑记 4 次，3 + 4 = 7 |
| 标签 | elements() = {旅行} | 手机只删除了它见过的票；电脑并发添加的票必须留下 |
| 正文 | text() = "新记" | 每个字符留下，顺序正确 |

每个用例有两类断言：状态相等（assertEquals(phone, computer)），以及可见结果正确（value / elements / text）。两类都要写。

各类型 equals 比较的字段不同：GCounter 只比较各设备的分量；ORSet 比较存活的票与墓碑；RGA 比较所有节点与墓碑。可见结果相同不代表状态相等。不要把可见结果相等当成同步完成。

## 2. 先少量操作，画完整传播路线

**假设**

手机先记 2 次，电脑先记 3 次。第一次手机发给电脑的消息丢失；电脑发给手机的消息送达。之后两边各再记 1 次，再同步。事情按这个顺序发生：

```text
① 手机记 2 次。手机状态：A2。手机不知道电脑。
② 电脑记 3 次。电脑状态：B3。电脑不知道手机。
③ 手机把 A2 发给电脑。消息丢失。电脑仍是 B3，仍不知道手机。
④ 手机保存一份自己的旧快照 delayedPhone：A2。
⑤ 电脑把 B3 发给手机。消息送达。手机 merge 后是 A2/B3。手机知道电脑的 3 次。
⑥ 手机再记 1 次。手机是 A3/B3。手机再保存一份快照 fromPhone：A3/B3。
⑦ 电脑再记 1 次。电脑是 B4。电脑仍不知道手机。
⑧ 电脑把 B4 发给手机。送达。手机是 A3/B4。
⑨ 电脑把 B4 重发给手机。手机再 merge 一次。手机仍是 A3/B4。
⑩ delayedPhone（A2）晚到电脑。这是电脑第一次收到手机的消息。电脑 merge 后是 A2/B4。
⑪ fromPhone（A3/B3）送达电脑。电脑是 A3/B4。
⑫ 手机的当前状态 A3/B4 送达电脑。电脑是 A3/B4。
```

④ 和 ⑥ 的快照能保留旧值，因为状态不可变：merge 返回新对象，不修改旧对象。

每次 merge 按一条规则计算：每个设备的分量取两边较大值。逐步演算：

| 步骤 | 动作 | 逐分量取大 | 结果 |
| --- | --- | --- | --- |
| ⑤ | 手机 ← B3 | A：2；B：max(0, 3) = 3 | A2/B3 |
| ⑧ | 手机 ← B4 | A：3；B：max(3, 4) = 4 | A3/B4 |
| ⑨ | 手机 ← B4（重发） | A：3；B：max(4, 4) = 4 | A3/B4（不变） |
| ⑩ | 电脑 ← A2（晚到） | A：max(0, 2) = 2；B：4 | A2/B4 |
| ⑪ | 电脑 ← A3/B3 | A：max(2, 3) = 3；B：max(4, 3) = 4 | A3/B4 |
| ⑫ | 电脑 ← A3/B4 | A：3；B：4 | A3/B4 |

最终两边都是 A3/B4。状态相等。value = 3 + 4 = 7。

**问题**

③ 丢失的消息必须按原操作重放吗？⑩ 的旧快照晚到，为什么不改变结果？

**解释**

1. 不需要重放原操作。手机的每次记数只增加 A 的分量。分量不会减少。
2. ⑥ 的新状态 A3 已包含 ① 的 2 次。把手机的新状态重新发给电脑，就能补齐丢失的内容。
3. ⑩ 的旧快照不改变结果。逐分量取大：max(3, 2) = 3。晚到的 2 不会让 3 变回 2。
4. ⑨ 的重发不改变结果。同一状态 merge 两次与 merge 一次相同。这条性质叫幂等。
5. 结论：重试负责最终送达；幂等保证重发与晚到安全。

打开练习里的 counterConvergesAfterALostDeliveryIsRetried。先算出期望总数 7，再逐行对照上面的时间线读断言。

## 3. 哪一条操作是在模拟网络

**假设**

事情按这个顺序发生：

```text
① 测试里没有网络，也没有服务器。
② 测试把每个状态保存在不可变对象里。
③ 测试按选定的顺序调用 merge。一次 merge 表示一条消息送达。
```

**问题**

丢包、重发、旧快照晚到分别怎样表达？为什么不用先搭服务器？

**解释**

三种网络事件各对应一种写法：

1. 丢包：跳过这次 merge，不调用。
2. 重发：用同一个状态做参数，merge 两次。
3. 旧快照晚到：先把旧对象存进局部变量，后面再 merge。

对应代码：

```java
GCounter delayed = phone;       // 留下旧快照
// 此处没有让电脑 merge(phone)，模拟未送达
phone = phone.merge(computer);  // 另一方向送达
computer = computer.merge(delayed).merge(delayed); // 旧消息重发
```

这段代码只示意三种写法。最终值要按具体时间线计算，见第 2 节。

状态不可变让轨迹可复现：delayed 在赋值后不会被任何后续操作修改。

再区分两类调用：

1. 本地用户操作：increment、add、remove、insert、delete。它们推进本设备的状态。
2. 收到对方状态：merge。它不产生新的用户操作。

例：电脑 merge 手机的 A2 后，电脑是 A2/B3。电脑的 B 分量仍是 3，不会变成 4。merge 只学习对方的分量，不增加本设备的分量。同步调用不能被统计成新的用户操作。

## 4. 三律的测试为什么还要选边界

**假设**

事情按这个顺序发生：

```text
① 标题规则（第 3 章）：编号相同就是平局。平局时来源 ID 较大者获胜。
② 实现有错误：平局时写成“保留自己的值”。
③ 测试只用编号 1 与编号 2 做检查：A1 对 B2，B1 对 A2。
④ 所有用例通过。平局分支从未执行。
```

**问题**

交换律的用例全部通过，能代表所有合法状态都正确吗？

**解释**

1. 不能。通过的用例只覆盖已选的状态对。
2. 平局要求两边编号相同、来源不同。③ 的每对用例编号都不同。平局分支从未执行。
3. 专门构造平局用例：编号相同，来源不同。例：A5 对 B5。正确规则让 B 获胜；② 的错误实现会让 A 获胜。
4. 再检查其余边界：状态与自己 merge（幂等）；空状态与有内容的状态 merge；三份状态按不同分组 merge（结合律）。

参考目录的 LatticeLawsTest 逐类型检查幂等、交换、结合三律。ConvergenceTest 用固定随机种子生成更多操作序列。固定种子让失败可以直接重放。

学习用例先选少量确定的轨迹，失败时能直接重放。随机测试再扩展覆盖。有限次测试通过不叫数学证明。

## 5. 增加一条能检验自己理解的轨迹

**假设**

已有测试覆盖三种轨迹：计数器的丢包与重试（第 2 节）；标签的并发添加留下（练习第二个用例）；正文的墓碑下挂着新字符（练习第三个用例）。你要再检查一件事：正文的旧快照晚到，已删除的字符不会回来。

故事按这个顺序发生：S 写出初始内容，手机删除一个字符，电脑插入一个字符，最后旧快照晚到。

```text
① S 写出正文 ab：a 的坐标是 (1,S)；b 的坐标是 (2,S)，挂在 a 后面。
② ab 送达手机和电脑。两边都持有节点 {a, b}，没有墓碑。
③ 手机保存一份旧快照 shared：节点 {a, b}，无墓碑。
④ 手机删除 b。手机：节点 {a, b}，墓碑 {(2,S)}。可见文本 a。
⑤ 电脑在 a 后面插入 X。X 的坐标是 (3,B)，挂在 a 后面。
   电脑：节点 {a, b, X}，无墓碑。可见文本 aXb。
⑥ 手机的状态送达电脑。电脑 merge 后是：节点 {a, b, X}，墓碑 {(2,S)}。
⑦ 电脑的状态送达手机。手机 merge 后是：节点 {a, b, X}，墓碑 {(2,S)}。
⑧ 旧快照 shared 晚到手机。手机再 merge 一次。
```

**问题**

这个新用例该先想方法名，还是先想这段故事？

**解释**

1. 先想故事，并先算出期望结果。
2. 再把故事写成上面的时间线。每一步只有一类动作：本地操作，或一条消息送达。
3. 最后才写 @Test 和方法名。

用具体值演算 ⑥⑦⑧：

```text
⑥ 节点取并集：{a, b} ∪ {a, b, X} = {a, b, X}。墓碑取并集：{(2,S)}。
   a 的子节点：X(3,B) 与 b(2,S)。坐标大的排在前面：X 先，b 后。
   遍历：a → X → b。b 有墓碑，不显示。可见文本 = aX。
⑦ 与 ⑥ 相同。两边状态相等，文本都是 aX。
⑧ 旧快照的节点是 {a, b}：并集不变，X 保留。
   旧快照没有墓碑：墓碑并集仍是 {(2,S)}，b 不复活。
   可见文本仍是 aX。
```

⑧ 只写了手机一侧。旧快照送达电脑的结果相同：shared 的节点与墓碑都是电脑状态的子集，merge 不改变状态。

期望结果：两边状态相等；text() 都是 aX；⑧ 之后仍是 aX。

写 @Test 时用 assertEquals 检查两类结果：assertEquals(phone, computer)；assertEquals("aX", phone.text())。不要先堆随机循环，再只断言非空。非空检查发现不了 b 复活，也发现不了 X 丢失。

## 读已有测试时追三件事

读已有测试时，按顺序追三件事：

1. 每个状态对象来自哪一次本地操作。
2. 哪条消息还没有送达。
3. 哪些信息决定期望结果。

这三件事对应测试里的局部变量、merge 顺序和断言。看清它们，就能独立添加一种轨迹。

注意本章用例的边界。以下情况没有被覆盖：同步之后持续有新写入；任意长时间的断网；从旧备份恢复；GC 之后再写入。这些用例通过不代表这些情况安全。

遇到两边不一致，按这个顺序排查：

1. 先检查各设备是否收到相同的消息。
2. 再检查本地操作的规则。
3. 再检查 merge 的规则。
4. 最后检查查询的规则：value、elements、text。
