# 第 5 步：笔记标签，取消后还能重新加吗？

**上一步**：上章让手机 A 和电脑 B 保留笔记标题的并发修改，不再丢失其中一个。

**本课任务**：给同一篇离线笔记添加“旅行”“工作”标签，支持取消、重新添加和同步。

**完成后**：写出一个集合：旧消息不会令已取消的标签重新出现，并发的新添加仍能保留。

**练习入口**：[learnning/ORSet.java](../learnning/ORSet.java) 和 [ORSetLearningTest.java](../../../../test/java/crdt/learnning/ORSetLearningTest.java)，按下面的任务填 TODO。

[← 目录](../README.md) ｜ 上一步：[版本向量与 MV 寄存器](04-版本向量与MV寄存器.md) ｜ 下一步：[RGA 文本](06-RGA文本.md)

**阅读约定**：本章只有两台设备：手机和电脑，简记为 **A（手机）**、**B（电脑）**。每次添加生成一张**票**（代码中的 `Tag`）。票由两项组成：设备 ID、该设备的添加序号。A 的第 1 次添加生成 (A, 1)，本章简写为 **A1**；B 的第 2 次添加生成 (B, 2)，简写为 **B2**。第 1 节说明为什么需要票，先记住写法即可。

## 1. 给“添加一次”一个身份

**假设**

事情按这个顺序发生：

```text
① A 添加标签“旅行”。此时 A 持有 {旅行}，B 没有记录
② A 同步给 B，B 收到“旅行”。此时 A、B 都持有 {旅行}
③ 断网。A 取消“旅行”。此时 A 持有 {}，B 不知道这次取消
④ B 没有做任何操作。此时 B 仍持有 {旅行}
⑤ 两台设备联网，互相同步
```

**问题**

两个集合怎样合并，才能让“旅行”保持取消状态？

**解释**

先试两种直接的做法，各算一遍：

1. 并集：A 持有 {}，B 持有 {旅行}，结果是 {旅行}。A 的空集合没有记录“取消”这件事。“旅行”重新出现，结果错误。
2. 交集：结果是 {}，“旅行”被删除，这一步正确。换一个顺序再算：A 添加“工作”，B 还没有收到，交集是 {}。一次新添加被删除，结果也错误。
3. 两种做法失败的原因相同：集合只记录“现在有什么”，没有记录“取消过什么”。

再试第三种做法：A 记录一个“已取消标签”集合，取消时把“旅行”这个名字放进去。接着⑤算两步：

1. 同步时，“旅行”在已取消集合中，旧添加被删除。这一步正确。
2. 用户重新添加“旅行”。这个名字仍在已取消集合中，新添加也被阻止。这一步错误。

结论：取消的对象应当是旧的那一次添加，不是“旅行”这个名字。给每次添加生成一张唯一的票，叫 `Tag`：

```text
(A, 1) = A 第一次添加，本章简写 A1
(A, 2) = A 第二次添加，本章简写 A2
(B, 1) = B 第一次添加，本章简写 B1
```

先在骨架的 `Tag` 内保存这两个字段，再实现它的方法。构造输入是副本 ID 和添加序号，返回一张不可变票；副本 ID 为空或缺失时拒绝构造。`replicaId()`、`seq()` 返回这两个值。两张票只有这两项都相同才相等，`hashCode()` 也使用它们，才能放进 `Set` 去重。

A1 和 A2 不相等，即使都代表“旅行”。还有两条约束：

1. 不同设备不能共用同一个写入 ID。
2. 同一设备不能丢失计数历史后从 1 重来。

违反任何一条，两次不同的添加会生成相同的票。旧的取消记录会错误地删除新添加。

## 2. 一份标签为什么要存多张票？

**假设**

事情按这个顺序发生：

```text
① A 添加“旅行”，生成票 A1。此时 A 持有 {旅行:{A1}}
② A 同步给 B，B 收到 A1。此时 B 持有 {旅行:{A1}}
③ 断网。A 取消“旅行”。A 只知道自己持有的 A1，所以只有 A1 被记为已取消
④ 同一段断网期间，B 再添加一次“旅行”，生成票 B1。此时 B 持有 {旅行:{A1,B1}}
⑤ 两台设备联网，互相同步
```

③ 和 ④ 互相不知道对方：A 取消时不知道 B1；B 添加时不知道 A1 已取消。

**问题**

A 的取消是否应该删除它不知道的 B1？

**解释**

1. 不应该。本章让 B1 保留。
2. 删除只处理取消时已经收到的票。
3. A 取消时只持有 A1，所以只有 A1 被删除。
4. A 以后收到 B1，再取消一次，B1 才被删除。
5. 这条规则叫 observed-remove：只删除已观察到的添加。
6. 取消者未观察到的并发添加会保留，所以也叫 add-wins。

注意边界：这不是“添加永远胜过删除”。这条规则只规定删除的范围。若产品要求并发取消也阻止新添加，要选择另一套语义。

为了执行这条规则，先在骨架中定义两份数据字段，再补操作方法：

```java
String replicaId;         // 本设备后续发票使用的身份
long seq;                 // 本设备最后发出的添加序号
Map<E, Set<Tag>> entries;  // 标签 → 当前仍存活的添加票
Set<Tag> tombstones;      // 已取消的票，叫墓碑
```

例如⑤合并后，“旅行”只剩 B1，A1 进入墓碑：

```text
entries    = {旅行: {B1}}
tombstones = {A1}
```

始终维持两个约束：`entries` 不保存空票集，也不保存已进入墓碑的票。有这个 key 就表示标签存在，后面的查询不用再次过滤。

基础阶段使用骨架的四参数内部构造器，只保存身份、seq、entries、tombstones。带 version/删除见证的六参数构造器留到第 9 章；本章 add/remove/merge 返回基本状态，不需要调用 CausalStamp。

先补 `empty(String replicaId)`：输入本设备身份，返回添加序号为 0、两份集合都为空的状态。空或缺失 ID 应拒绝；身份有效后创建状态即可。

需要检查后续写入身份时，`replicaId()` 无输入，直接返回保存的本地 ID；它不会改变集合。

所有修改返回新 `ORSet<E>`，原状态不变。复制外层 `Map` 还不够：要改变某个标签的票集时，也复制那份 `Set`，不要改到旧快照共享的数据。

## 3. 用户点“添加旅行”：实现 add

**假设**

事情按这个顺序发生：

```text
① A 从空状态开始。此时 seq=0，没有任何标签，也没有墓碑
② A 添加“旅行”，生成 A1。此时 seq=1，A 持有 {旅行:{A1}}
③ A 又添加一次“旅行”，生成 A2。此时 seq=2，A 持有 {旅行:{A1,A2}}
```

**问题**

第二次添加只要忽略就行吗？

**解释**

1. 不能忽略。
2. 本地显示仍是一个“旅行”。
3. 第二次点击是新的添加历史。
4. 它可能与另一台设备的取消并发。
5. 没有新票，这次添加会被旧的取消记录删除。

因此 `add(E element)` 接收标签，返回包含新添加的状态。每次执行都生成一张新票：

```text
第一次：seq=1，entries={旅行:{A1}}
第二次：seq=2，entries={旅行:{A1,A2}}
```

按需求把 TODO 拆成这几步：

```text
nextSeq = seq + 1
newTag = Tag(replicaId, nextSeq)
复制 entries
复制 element 原有的票集，没有则从空集开始
把 newTag 加进去，写回 element
返回新状态，保存 nextSeq，沿用旧墓碑
```

边界条件：`seq` 计数到 `Long.MAX_VALUE` 时拒绝继续添加，不能绕回旧序号。绕回会让新添加拿到旧票，旧墓碑会删除它。`element` 不承担添加身份：字符串相同只决定归到哪个标签下面。

## 4. 用户点“取消旅行”：实现 remove

**假设**

事情按这个顺序发生：

```text
① A 添加过两次“旅行”。此时 seq=2，entries={旅行:{A1,A2}}，tombstones={}
② A 取消“旅行”。A1、A2 进入墓碑。此时 entries={}，tombstones={A1,A2}
③ B 还持有旧状态 {旅行:{A1}}。B 的旧消息之后可能重发到达 A
```

**问题**

只从 `entries` 删掉“旅行”，够不够？

**解释**

不够。先算没有墓碑的情况：

1. 假设取消后不留墓碑，A 是 entries={}，tombstones={}。
2. B 的旧消息到达，带着票 A1。
3. 合并取并集：entries={旅行:{A1}}。
4. A 没有证据识别 A1 已取消。“旅行”重新出现。

再算有墓碑的情况：

1. A 的墓碑是 {A1,A2}。
2. 旧消息到达，并集后“旅行”的票集是 {A1}。
3. 票集删除墓碑票：A1 被删除，票集变空。
4. 空票集的 key 被删除。“旅行”保持取消。

`remove(E element)` 接收标签，返回取消本地可见添加后的状态：

```text
取消前：entries={旅行:{A1,A2}}，tombstones={}
取消后：entries={}，tombstones={A1,A2}
```

实现时分四步：

1. 取 `entries.get(element)`。
2. 没有票：当前看不到这个标签，直接返回等价状态。
3. 有票：复制 entries 和 tombstones，把这些票加进墓碑，并从 entries 删除这个 key。
4. 返回新状态。`seq` 不变：取消不生成新票。

还有两条边界：

1. 不删除“未来可能属于旅行的票”。这些票不在本地历史中。
2. 不删除旧墓碑。旧消息还可能到达。

此时再次 `add("旅行")`，接着②算一遍：

```text
seq：2 → 3，生成 A3
entries={旅行:{A3}}，tombstones={A1,A2}
```

墓碑只含 A1、A2，不包含 A3，因此 A3 存活，完成“添加 → 取消 → 重加”。

## 5. 标签栏需要查询：实现 contains、elements、size

**假设**

事情按这个顺序发生：

```text
① A 添加“旅行”，生成 A1。此时 A 持有 {旅行:{A1}}
② A 添加“工作”，生成 A2。此时 A 持有 {旅行:{A1}, 工作:{A2}}
③ A 同步给 B，B 收到 A1、A2
④ B 也添加“旅行”，生成 B1。此时 B 持有 {旅行:{A1,B1}, 工作:{A2}}
⑤ 两台设备再次同步。两边存储都是 {旅行:{A1,B1}, 工作:{A2}}
⑥ 页面读取存储，要画两个标签，并判断“旅行”按钮是否选中
```

**问题**

`size()` 应返回 3 还是 2？页面可以直接拿到内部可修改集合吗？

**解释**

1. 返回 2。
2. 票是同步历史，标签是业务内容。
3. “旅行”有两张票，仍是一个标签。
4. 前面维持了“只有存活票的 key 才存在”的约束，所以查询不用再次过滤。

三个方法各回答一个问题：

```java
boolean contains(E element)  // 输入标签，返回 entries 是否有这个 key
Set<E> elements()            // 无输入，返回可见标签集合，即 entries 的 key
int size()                  // 无输入，返回标签数量，即 entries 的 key 数
```

这些方法是为页面读取而来，不生成新票、不修改状态。返回的集合也不能允许调用方改动内部状态：可返回不可修改视图或不可修改副本。骨架与参考实现都用不可变状态约束来保护它。

## 6. 联网交换状态：实现 merge

**假设**

事情按这个顺序发生：

```text
① A 添加“旅行”，生成 A1。A 同步给 B。此时两台设备都持有 {旅行:{A1}}
② 断网。A 取消“旅行”。此时 A：entries={}，tombstones={A1}
③ 同一段断网期间，B 重新添加“旅行”，生成 B1；再添加“工作”，生成 B2。
  此时 B：entries={旅行:{A1,B1}, 工作:{B2}}，tombstones={}
④ 两台设备联网，A 收到 B 的状态
```

② 和 ③ 互相不知道对方：A 取消时不知道 B1、B2；B 添加时不知道 A1 已取消。

**问题**

怎样既阻止 A1 重新出现，又保留 B1 和“工作”？

**解释**

`merge(ORSet<E> other)` 输入对方状态，返回合并后的新状态；接收者仍使用自己的副本 ID 写入。空参数应拒绝。

核心步骤是“先汇总，再剪枝”：

```text
1. 对每个标签，把两边添加票取并集。
2. 把两边墓碑取并集。
3. 每个标签的票集移除全部墓碑票。
4. 若某个标签没剩票，移除这个 key。
```

把④代入，手算这一轮：

| 阶段 | 旅行的票 | 工作的票 | 墓碑 |
| --- | --- | --- | --- |
| 汇总 | A1、B1 | B2 | A1 |
| 剪枝 | B1 | B2 | A1 |

逐标签检查：

1. 旅行：并集是 {A1,B1}，删除墓碑票 A1，剩 {B1}。标签保留。
2. 工作：并集是 {B2}，与墓碑没有交集。标签保留。
3. 结果：entries={旅行:{B1}, 工作:{B2}}，tombstones={A1}。

再处理 `seq`，规则有两条：

1. 合并不生成新票。`seq` 是**本设备生成添加票的序号**，不能直接拿对方的 `seq` 当自己的。本例中 A 的 `seq` 保持 1，下次添加仍生成 A2。
2. 收到自己身份的旧状态或旧票时例外：把本地 `seq` 提升到已知本设备最大序号。参考实现检查三处：同身份状态的 `seq`、对方存活票中的本设备票、对方墓碑中的本设备票。这样防止下次复用已经生成过的票。

边合并边修改共享票集会破坏旧快照；仍用复制后的集合做并集与剪枝。最终再检查“无空票集、无墓碑票”的约束。

## 7. 两边同步完了吗：实现 equals 和 hashCode

**假设**

事情按这个顺序发生：

```text
① A 添加“旅行”，生成 A1。此时 A 保存 {旅行:{A1}}
② B 没有收到 A 的消息，也添加“旅行”，生成 B1。此时 B 保存 {旅行:{B1}}
③ 两台设备的页面都显示“旅行”
```

**问题**

文本一样，就能认定两个状态相等吗？

**解释**

1. 不能。
2. 反证：假设只看文本就判定相等。
3. 之后收到“删除 A1”的消息。
4. A 的“旅行”失去唯一的票，标签被删除。
5. B 仍有 B1，标签保留。
6. 文本相同的两个状态，合并结果不同。
7. 票和墓碑影响未来合并，必须参与比较。

`equals(Object other)` 接收任意对象，返回是否是同类、且 `entries` 和 `tombstones` 都相等。`hashCode()` 使用同样两份数据。副本 ID 和本地 `seq` 不参与：它们决定下一次本地写入，不决定当前共享集合状态。

调试时还要看见票和墓碑，因此 `toString()` 无输入，返回包含 entries、tombstones、副本 ID 和 seq 的状态描述；`Tag.toString()` 返回设备 ID 与序号的描述。它们只用于观察，不承担相等判断。

完整参考实现还带有第 9 章的删除见证和 `version`，OR-Set 的 `equals` 没有比较它们。因此这里的相等不能替代全部回收元数据的核对。

## 8. 把这篇笔记的操作串起来

**假设**

操作按这个顺序发生，每次调用都把返回的新状态保存回本变量：

```text
① A 添加“旅行”
② B 接收 A 的状态
③ A 取消“旅行”
④ B 添加“旅行”，再添加“工作”
⑤ A 接收 B 的状态
⑥ A 再次取消“旅行”
⑦ A 重新添加“旅行”
```

先在纸上写出票，再填代码预测结果：

```java
ORSet<String> a = ORSet.<String>empty("A").add("旅行"); // A1
ORSet<String> b = ORSet.<String>empty("B").merge(a);
a = a.remove("旅行");              // 墓碑 A1
b = b.add("旅行").add("工作");    // B1、B2
a = a.merge(b);                     // 旅行 B1，工作 B2
a = a.remove("旅行");              // 又收到并取消 B1
a = a.add("旅行");                 // 新票 A2
```

**问题**

最后“旅行”为什么存在？“工作”为什么不受取消影响？

**解释**

逐行演算：

| 行 | a 的状态 | b 的状态 |
| --- | --- | --- |
| 1 | seq=1，entries={旅行:{A1}}，tombstones={} | 尚未创建 |
| 2 | 不变 | seq=0，entries={旅行:{A1}}，tombstones={} |
| 3 | seq=1，entries={}，tombstones={A1} | 不变 |
| 4 | 不变 | seq=2，entries={旅行:{A1,B1}, 工作:{B2}}，tombstones={} |
| 5 | seq=1，entries={旅行:{B1}, 工作:{B2}}，tombstones={A1} | 不变 |
| 6 | seq=1，entries={工作:{B2}}，tombstones={A1,B1} | 不变 |
| 7 | seq=2，entries={旅行:{A2}, 工作:{B2}}，tombstones={A1,B1} | 不变 |

检查两处结果：

1. 第 5 行：A 合并 B 时，B 的 entries 含本设备票 A1，A 的 `seq` 提升到 1，等于原值，所以下次添加才生成 A2。
2. 第 7 行：墓碑是 A1、B1，不含 A2。“旅行”靠 A2 存活。
3. `remove` 只处理指定标签当时可见的票。“工作”的票 B2 不在“旅行”的票集中，不受取消影响。

最终 `elements()` 是“旅行”“工作”，墓碑是 A1、B1。

标记为第 9 章的 `version()`、`tombstoneCount()`、`gc()` 暂时留到那里；本章测试不依赖这些方法。先完成本章的核心 TODO，再对照 [完整参考 ORSet.java](../ORSet.java) 核对复制集合、序号提升和剪枝细节。

参考中的 `seq` 只在添加时推进；`version` 记录添加和有效删除的修改进度，删除不存在的标签不推进。二者不是同一个计数。墓碑何时可以回收、删除见证怎么记录，留到 [第 9 章：墓碑 GC](09-墓碑GC.md)。
